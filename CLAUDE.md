## Build & Run Commands

```bash
# Build (skip tests)
mvn clean package -DskipTests

# Run all tests, with the coverage floor (~3.5 min: 4 test JVMs, slowest classes first)
mvn verify

# The inner loop: everything but the classes tagged `slow` (the golden manifests and the suites
# that generate many whole projects), no coverage (~2 min)
mvn test -Pquick

# One test JVM instead of four (-Dtest.forks=N for another number)
mvn verify -Dtest.forks=1

# Run a single test class
mvn test -Dtest=ProjectGenerationIntegrationTests

# Run a single test method
mvn test -Dtest=ProjectGenerationIntegrationTests#kafkaDependencyInjectsConfigFiles

# Run the application
java -jar target/offline-spring-init-1.0.0-SNAPSHOT.jar

# Verify the running service
curl http://localhost:8080/metadata/client
curl http://localhost:8080/actuator/health

# Generate a test project via API
curl -o test.zip "http://localhost:8080/starter.zip?dependencies=web,kafka"

# Hot-reload metadata after DB change (no restart needed)
curl -X POST http://localhost:8080/admin/refresh
```

### How the test suite runs (2026-11)

- **Four JVMs at once** (`test.forks` in the pom, surefire `forkCount`; `reuseForks`): classes are spread over them, one after another within a JVM. Each JVM has its own in-memory `testdb`, seeded by its first context. `runOrder=balanced` starts the slowest classes first, by the last run's times in `.surefire-*` (git-ignored); the first run on a machine has none. Measured on a 20-core machine: 9:22 in one JVM, 4:31 in four, 3:30–3:56 with the shared contexts and the balanced order; six JVMs were no faster.
- **Two shared Spring contexts.** A context is cached by its configuration, so a class that says exactly what another says reuses its context instead of starting one (≈8 s each, ≈30 s for a JVM's first). `@IntegrationTest` (server on a random port, MockMvc, `TestInvokerConfiguration`) is the generation tests'. `@CatalogTest` (MockMvc, no server) is for the classes that **change the catalog** — the admin API, imports, the seeder, the catalog and template syncs: they reload what the application caches from it, and in the generation tests' context that left "Unknown dependency 'data-jpa'" behind for the next class. A class with its own properties or an extra bean (`AdminIdentityAndHistoryTests`, `UserInfoGateTests`, `LiveSchemaIntegrationTests`, `GlobalErrorHandlingTests`, the smoke suites) keeps its own context. **A new test class should use one of the two annotations**; a test in a shared context must not assume it ran first (`PopularDependenciesAndLivePreviewTests` counts through the service, since the endpoint's top ten can hide a dependency other classes pushed down).
- **`@Tag("slow")`** on `FullstackStarterIntegrationTests`, `FullstackPagesIntegrationTests`, `FullstackGoldenOutputTests`, `WizardGoldenOutputTests`, `BackendPatchTests`, `FullstackPatchTests`: left out by `-Pquick` (`test.excludedGroups=slow`, `jacoco.skip=true`).
- **Coverage** (JaCoCo) is reported and enforced in `verify`; `mvn test` only records it, `-Pquick` not even that.
- Not done: what each context does on start is mostly a cold JVM and Hibernate; the seed runs once per JVM and the syncs on a seeded database only compare, so skipping them would save little.

## Architecture

This app wraps the Spring Initializr framework (`initializr-web` + `initializr-generator-spring` v0.23.x). The framework handles the REST API and ZIP generation; this codebase adds:

1. **A database-driven dependency catalog** — all dependency definitions, file contributions, build customizations, and sub-options live in an H2 database (file-backed in production, in-memory for tests)
2. **A single dynamic generation config** (`DynamicProjectGenerationConfiguration`) — reads from DB at generation time, replacing what used to be 8 separate hardcoded extension classes
3. **An admin REST API** (`/admin/*`) — full CRUD for all DB tables + a `/admin/refresh` endpoint to hot-reload the dependency metadata cache

**Admin tokens are stateless.** `POST /admin/login` returns an HMAC-signed token carrying its own expiry (`admin/AdminTokenStore`: key = `admin.token-secret`, else derived from `admin.password`; lifetime `admin.token-ttl`, default 12h), so any replica behind a load balancer accepts a token another one issued. Nothing is stored, so there is nothing to clean up; `/admin/logout` is a no-op and changing the password (or secret) invalidates every token. Every replica must share the password/secret. The tokens used to be an in-memory set per JVM, which logged users out at random with two QA instances. Pinned by `AdminTokenStoreTest`.

### Generation Pipeline

When a project is generated, the framework spins up a child Spring application context for that request and calls every `ProjectGenerationConfiguration` registered in `META-INF/spring.factories`. Only one is registered: `DynamicProjectGenerationConfiguration`, which contributes three beans:

- **`dynamicFileContributor`** (`ProjectContributor`) — for each selected dependency (plus the special `__common__` entry), writes/merges all associated `FileContributionEntity` records into the generated project
- **`dynamicDeleteContributor`** (`ProjectContributor`, `@Order(LOWEST_PRECEDENCE)`) — runs after everything else to delete files registered with `DELETE` type (e.g. `application.properties` written by the framework). `DELETE` is handled **only** here, never in the write pass, and it applies the same `isGatedOut` sub-option/`javaVersion` gating and the same `resolveTargetPath` (`{{packagePath}}`) resolution as the write pass — the two share one predicate so they can't drift
- **`dynamicBuildCustomizer`** (`BuildCustomizer<MavenBuild>`) — applies all `BuildCustomizationEntity` records (add dependency, exclude dependency, add repository, import a BOM). Like the file contributor, it skips a record whose `subOptionId` is set unless that sub-option was selected (`optionsContext.hasOption(depId, subOptionId)`) — e.g. `mapstruct`'s processor deps, or a database dep's secondary-datasource config, are added only with the matching sub-option

### FileContributionEntity — File Types

| Type | Behavior |
|------|----------|
| `STATIC_COPY` | Writes content verbatim to target path |
| `YAML_MERGE` | Deep-merges YAML into the target file (creates if absent). Blank / comments-only content loads as `null` in SnakeYAML and is treated as an empty map, so such a row is a no-op rather than an NPE |
| `TEMPLATE` | Applies substitution variables then writes |
| `DELETE` | Deletes target file (runs at LOWEST_PRECEDENCE, after framework writes) |

### Version Gating — `java_version` / `node_version`

A `FileContributionEntity` may pin itself to a single language-runtime version, so one
target path resolves to an entirely different file per selected version. Both columns
default to null (= applies to every version):

- **`java_version`** (backend) — checked in `DynamicProjectGenerationConfiguration`; the row
  is skipped unless it equals `description.getLanguage().jvmVersion()`. Used for the backend
  `Dockerfile` (`Dockerfile-java17.mustache` vs `Dockerfile-java21.mustache`, both targeting `Dockerfile`).
- **`node_version`** (frontend) — the frontend mirror, added in `V17`. Checked in
  `FrontendProjectGenerator.nodeVersionMismatch`; the row is skipped unless it equals
  `FrontendProjectDescription.getNodeVersion()`. Used for the frontend `Dockerfile`
  (`static-configs/frontend/common/Dockerfile-node{18,20,22}`, all targeting `Dockerfile`).

To add a Node version, seed a matching `Dockerfile-node<v>` row in `catalog/frontend/file-contributions.json`
— a version with no matching row generates no Dockerfile. Both columns round-trip through admin export/import.

### Local Vault connection (every backend)

Every generated backend — `/starter.zip`, the wizard, each multi-module module and the fullstack `backend/` — can read its secrets from Vault on a developer's machine. It is all `__common__` catalog rows, so it reaches every path through `DynamicProjectGenerationConfiguration`:

- **pom** — an `ADD_BOM` row imports `spring-cloud-dependencies` (`<spring-cloud.version>2023.0.3</spring-cloud.version>`, right for Boot 3.2.x; edit the row when a Boot 3.4/3.5 version is added), and an `EXCLUDE_DEPENDENCY` row adds `spring-cloud-starter-vault-config` (BOM-managed, no version) without `httpclient5`.
- **`application.yaml`** — `templates/application-base.mustache` turns Vault off by default: `spring.cloud.vault.enabled: false` and `management.health.vault.enabled: false` (written into the base template, not a `YAML_MERGE` row, so the file keeps its comments).
- **`src/main/resources/application-vault-local.yaml`** (`templates/vault/`) — the `vault-local` profile: Vault on, TOKEN auth, namespace `${VAULT_NAMESPACE:{{department}}/int-lan-01}`, `spring.config.import: vault://secretvars/{{artifactId}}`.
- **`config/VaultLocalEnvironmentPostProcessor.java`** + **`META-INF/spring.factories`** registering it — activates `vault-local` when `VAULT_TOKEN` is in the environment or in a `.env` in the working directory (never under the `test` profile), ordered before config-data loading so the profile file is read.
- **`.env`** (`templates/vault/env.mustache`, MUSTACHE: an empty `VAULT_TOKEN=` under "local-only, do not commit" comments, and a commented-out `VAULT_NAMESPACE={{department}}/qa-lan-01` naming the `{{department}}/int-lan-01` default — `Properties.load` skips the `#` lines) at the project root, git-ignored by the `dynamicGitIgnoreCustomizer` bean — it adds a `Local secrets` section with `.env` whenever a selected, non-gated row targets `.env`, so deleting that row in admin drops the ignore entry too. The fullstack root `.gitignore` names `backend/.env` (never a bare `.env`, which would hide the frontend's committed `.env` files).

**Upgraded DBs** keep their old `__common__` rows and `application-base` content until re-seeded or edited in admin. Pinned by `generatedProjectContainsLocalVaultConnection`, the fullstack/multi-module checks and `DataSeederTest`; built for real by `GeneratedBackendBuildSmokeTests`.

### Template Substitution

`TEMPLATE` contributions are rendered through a real Mustache engine (`com.samskivert:jmustache`, `escapeHTML=false`). `FileContributionEntity.SubstitutionType` has two values:

- **`MUSTACHE`** — render content with the unified context below
- **`NONE`** — write content verbatim

The context exposed to every MUSTACHE template is:

| Key | Meaning |
|-----|---------|
| `artifactId`, `groupId`, `version`, `packageName` | straight from `ProjectDescription` |
| `packagePath` | `packageName` with `.` → `/` (also available in Target Path — resolved separately) |
| `javaVersion` | `description.getLanguage().jvmVersion()` — e.g. `"17"`, `"21"` |
| `packaging` | `description.getPackaging().id()` — e.g. `"jar"`, `"war"` |
| `has<Dep>` | `true` for every selected dep. Dep id is PascalCased: `kafka` → `hasKafka`, `mail-sampler` → `hasMailSampler` |
| `opt<Dep><Option>` | `true` for every selected sub-option. e.g. `optKafkaConsumerExample` |

This unlocks conditional file content — e.g. a single template can gate a block on a sub-option using `{{#optKafkaConsumerExample}}…{{/optKafkaConsumerExample}}` instead of requiring a separate `FileContributionEntity` row per variation.

The table above is the backend-dependency subset. For the **complete** variable catalog across all three render contexts (backend dependency, fullstack entity, frontend) — every key, where it's derived (with file:line), the path-vs-content substitution rules, and authoring walkthroughs (add a template, conditional/sub-option gating, version gating) — see [`docs/MUSTACHE_GUIDE.md`](docs/MUSTACHE_GUIDE.md).

### DataSeeder — First-Startup Seeding

`src/main/java/com/menora/initializr/db/DataSeeder.java`

Runs at startup as a `SmartInitializingSingleton`. If all DB tables are empty it loads the dependency catalog from JSON manifests under `src/main/resources/catalog/` (backend) and `src/main/resources/catalog/frontend/` (frontend) and inserts them as DB records. This bootstraps the system; after seeding, records can be modified via the admin API without touching the filesystem.

**Catalog manifests** (DTOs in `db/seed/CatalogManifests.java`). The same five generic loaders read both the backend manifests under `catalog/` (stamped `ProjectKind.BACKEND`) and the frontend manifests under `catalog/frontend/` (stamped `ProjectKind.FRONTEND`) — each `load*(path, kind)` takes the manifest path and the kind to stamp on every row:

| Manifest | Replaces | Notes |
|----------|----------|-------|
| `dependencies.json` | `seedDependencyCatalog()` | Groups + entries; `compatibilityRange`/`starter` are plain fields. FE entries carry no Maven coords; the three React-19-sensitive design systems (`design-mui`/`design-chakra`/`design-mantine`) set `compatibilityRange: "[18.0.0,19.0.0)"`. `design-menora-digital` (the Menora Mivtachim customer-site brand system, see *Menora Digital* below) is plain CSS and carries no range |
| `file-contributions.json` | common + per-dep file contributions | Each row points at its content file via `contentResource` (a classpath path under `static-configs/*` or `templates/*`); the content itself stays in that file. Small inline strings (FSD barrels, layer READMEs, `.env` templates) use the `content` field instead. `DELETE` rows have no `contentResource`. An optional `javaVersion` (backend) or `nodeVersion` (frontend) field pins a row to one runtime version — see *Version Gating* above. `application.yaml` base keeps `sortOrder: -1`, the `application.properties` `DELETE` keeps `sortOrder: 9999` |
| `build-customizations.json` | `seedBuildCustomizations()` / FE `feNpm`/`feVitePlugin`/`feNpmScript` | `type` = `ADD_DEPENDENCY` / `EXCLUDE_DEPENDENCY` / `ADD_REPOSITORY` / `ADD_BOM` (backend; `ADD_BOM` = `mavenGroupId`/`mavenArtifactId`/`version`, imported into `<dependencyManagement>` with the version in a pom property named after the artifact — `spring-cloud-dependencies` → `spring-cloud.version`) or `ADD_NPM_DEPENDENCY` / `ADD_VITE_PLUGIN` / `ADD_NPM_SCRIPT` (frontend). FE rows reuse the Maven columns: npm dep = `mavenArtifactId` (package) + `version` (semver) + `scope` (`dev`/blank) + optional `subOptionId` gate; vite plugin = `mavenGroupId` (import path) + `mavenArtifactId` (binding) + `version` (call expr); npm script = `mavenArtifactId` (name) + `version` (command) |
| `sub-options.json` | `seedSubOptions()` / FE `feSubOption` | |
| `compatibility.json` | `seedCompatibilityRules()` / FE `feCompat` | one file per kind: `catalog/compatibility.json` (backend) and `catalog/frontend/compatibility.json` (FE) |

The loaders (`loadDependencyCatalog`, `loadFileContributions`, …) are generic — to change either catalog, edit the JSON, not Java. **Still seeded from Java helpers** in `DataSeeder`: starter/module templates, color palettes (`seedColorPalettes`), version definitions (`seedVersionsIfMissing`), and entity template sets (`templates/fullstack/*/manifest.json`). Departments and fullstack examples (`catalog/fullstack-examples.json`) are table-scoped seeds in the same pre-guard path. Color palettes and versions run in the pre-guard "if missing" path (idempotent per-row), so they are intentionally not folded into the all-or-nothing catalog load.

### Fullstack Generation — Two-Layer Reuse

`POST /starter-fullstack.zip` (`FullstackStarterController`) generates a `backend/` + `frontend/` pair from a list of user-defined entities. Both halves are **built on top of the standalone generators** rather than reimplementing them — entity scaffolding is the only fullstack-specific layer:

- **Backend** — runs through the standard Initializr `ProjectGenerationInvoker`, so `DynamicProjectGenerationConfiguration` applies the dependency catalog as usual; `FullstackProjectGenerationConfiguration` (registered in `spring.factories`, short-circuits when `EntityDefinitionContext.isEmpty()`) adds per-entity Java from the `spring-jpa-crud` entity template set.
- **Frontend** — `renderFrontend` first calls `FrontendProjectGenerator.renderInto(dir, desc)` to lay down the standalone FSD substrate (tooling configs, layer barrels + READMEs, `index.html`, `.gitignore`, dev `.env`/Vite proxy). It then deletes the substrate's `src/pages/home` and renders the `react-tailwind-crud` template set **as an overlay** — only the per-entity CRUD files + the fullstack-owned shared UI and Tailwind-v4 styling stack (`package.json`/`vite.config`/`index.css`/`tsconfig`/`main.tsx`/`App.tsx`), rendered last so it overwrites the substrate where paths collide. Per-entity templates are rendered with `EntityScaffoldContext` merged with `FrontendMustacheContext` (so they see both entity naming/field view-models and dep/palette/version flags).

So the FE template set is intentionally a thin **overlay**, not a full project — substrate files live in `catalog/frontend/*` and `templates/frontend/*`, edited once. (Known follow-up: the v4 styling stack stays overlay-owned because the standalone `style-tailwind` dep is still v3; unifying it would let the substrate own `package.json`/`vite.config` too. Since *Round 9* an upgraded DB's template rows follow the shipped ones on start — see *Template sync*.) Because the overlay overwrites the substrate's `package.json`, `renderFrontend` finishes with `FrontendProjectGenerator.mergeSubstrateTooling(dir, deps)`, which folds the `__common__` npm build customizations (eslint / prettier / husky / lint-staged deps and scripts) back into the overlay file **without overriding its pins** (`PackageJsonBuilder.merge`) — otherwise the `eslint.config.js` / `.husky/pre-commit` the substrate wrote reference packages that are never installed. The overlay `package.json.mustache` reads `{{reactPackageVersion}}` / `{{reactTypesVersion}}` (and `{{nodeVersion}}` for `engines`), so it follows the selected React version.

**Frontend ↔ backend wiring.** The generated frontend always calls same-origin `/api/...` — `VITE_API_BASE_URL` is empty in both overlay `.env` files. In dev the overlay's `vite.config.ts.mustache` (a MUSTACHE row, so it keeps the substrate's `basePath`/`apiBaseUrl`/`host: true` instead of clobbering them) proxies `/api` to the backend; in production the shared `static-configs/frontend/common/nginx.conf` has a `location /api/ { proxy_pass ${API_UPSTREAM}; }` block that `entrypoint.sh` substitutes at container start (`-e API_UPSTREAM=http://backend:3000` — the backend image listens on its `PORT` — default `http://localhost:8080`). The generated `CorsConfig` is therefore **off by default** and reads `app.cors.allowed-origins` (comma-separated) for the only case that needs CORS — a frontend built with `VITE_API_BASE_URL` pointing at the API directly. The API client rejects a non-JSON `content-type` so a missing proxy fails with a pointed message rather than a `SyntaxError` on `index.html`. Pinned by `generatesBackendAndFrontendForTwoEntities`.

**Generated API error contract.** Every scaffolded endpoint answers errors as RFC-7807 `ProblemDetail` (`application/problem+json`) from one non-perEntity `web/ApiExceptionHandler` (`@Order(HIGHEST_PRECEDENCE)`, so it beats the `validation` dep's `ValidationExceptionHandler` for the exceptions it declares): 404 for `web/ResourceNotFoundException` (thrown by `Service.findById`), 409 for `web/ResourceConflictException` (a `create` with a client-supplied key that `existsById` — `save()` would otherwise silently merge over the row) and for `DataIntegrityViolationException` (detail classified from the driver message: unique → "already exists", FK, not-null), 400 for bean validation with the per-field map under the `errors` property (the FE `api-client` maps it to `ApiError.fieldErrors`), unreadable bodies, type mismatches, `PropertyReferenceException` and any service `IllegalArgumentException`. Controllers carry **no** local `@ExceptionHandler`s. `?sort=` is whitelisted per controller (`SORTABLE` = every scalar DTO column + audit columns; unknown → 400) and the default sort is **all** PK columns; text search escapes `%`/`_`/`\` (`escapeLike`, `ESCAPE '\'`) and lowercases with `Locale.ROOT`. The slice test uses `@MockitoBean` from Boot 3.4 (`useMockitoBean`). Pinned by `fullstackEndpoint_hardensGeneratedApi`.

**Generated frontend forms and data hook.** Each feature gets `model/validate.ts` (`EntityValidate.ts.mustache`, re-exported by the feature barrel) with `validate<Entity>(value)`, derived from the same field metadata as the DTO's Bean Validation (required, `length`, `min`/`max`, `pattern` anchored as `^(?:…)$`, email, required relation FKs; a generated PK is never checked, a client-supplied one is required; the `blank` helper is emitted only when `hasBlankChecks`, because the generated lint forbids unused vars), and `EntityPage.save` runs it before calling the API, showing messages under the fields and clearing a field's message as soon as it is edited. `FormDrawer` is a real `<form noValidate>` (Enter submits, Save is `type="submit"`). `useResource.reload` drops out-of-order responses via a request counter, and `Table`/`CardGrid` show the skeleton only on the first load, keeping (dimmed) rows during a refetch. Pinned by `fullstackEndpoint_formValidatesClientSideAndDataHookGuardsStaleResponses`.

#### Entity model — fields, constraints, relations

A request entity (`EntityDefinition`, validated/converted from the wire by `FullstackRequestValidator`) has **fields** and **relations**:

- **Fields** (`FieldDefinition`) — `type` (`FieldType`: STRING/TEXT/LONG/INTEGER/BOOLEAN/LOCAL_DATE/LOCAL_DATE_TIME/BIG_DECIMAL/UUID/ENUM, and since *Round 9* LOCAL_TIME/INSTANT/MONEY/MARKDOWN/FILE/IMAGE), `primaryKey`/`generated`, `required`, `unique`, `length` (STRING only), and constraints `min`/`max` (`BigDecimal` on the wire and in `FieldDefinition`; numeric only, min ≤ max; whole numbers on LONG/INTEGER — and inside the int range for INTEGER — while BIG_DECIMAL takes decimals. `EntityScaffoldContext` renders both as strings so `@Min(0)`, `@DecimalMin(value = "0.5")`, the form's `min="0.5"` and the TS validator splice the same literal; the form adds `step="any"` on BigDecimal), `pattern` (STRING regex, validated compilable), `email` (STRING). **TEXT** is long text → a SQL `TEXT` column (`columnDefinition`, not `@Lob`, so search's `lower()`/`LIKE` works) rendered as a `<textarea>`; it joins `stringFields` so it stays searchable. **UUID** maps to the fully-qualified `java.util.UUID` (null import — the FQN keeps the Repository/Service compiling without a per-field import block) and may be `generated` (→ Hibernate `@UuidGenerator` instead of `IDENTITY`). Constraints render as Bean Validation on the **DTO** (`@Min`/`@Max` on integral, `@DecimalMin`/`@DecimalMax` on `BigDecimal`, `@Pattern`/`@Email` on strings) gated on the `validation` starter via `hasValidation`, and as HTML input attributes (`min`/`max`/`pattern`/`type="email"`) in the form. The regex is escaped once (`patternEscaped`) for both Java and JS string literals. **`defaultValue`** (String, optional) is type-checked in the validator per `FieldType` (integral/decimal parse, `true`/`false`, ISO date/date-time, `UUID.fromString`, ENUM ∈ `enumValues`, STRING/TEXT within `length`; rejected on a `generated` PK; errors name the field) and canonicalized. `fieldViewModel` exposes `hasDefault`/`defaultJava`/`defaultTs`: the entity field gets a Java initializer (`private String status = "draft";`, both backend sets), the DTO's `toEntity` skips a null so an omitted field keeps it, the FE `EntityPage` pre-fills `newDefaults()` on New (`hasFieldDefaults`), and `seedExpression` uses it for non-key, non-unique fields. Pinned by `fullstackEndpoint_rendersFieldDefaults`. **`enumLabels`** (`Map<String,String>`, ENUM only, optional) gives a constant its display label (`{"OPEN": "פתוח"}`; keys matched case-insensitively, canonicalized to the upper-cased constant; blank/>80-char/unknown-key → 400 naming the field and key). `fieldViewModel` puts `label` (custom, else `humanizeConstant`: `IN_PROGRESS` → "In progress") and `labelTs` (single-quote-escaped) on every `enumValues` entry plus a field-level `hasEnumLabels`; the entity view adds `breakdownIsEnum`/`breakdownEnumTypeName`/`kanbanEnumTypeName` and each `kanbanColumns` lane a `labelExpr` (a quoted literal, or `t('trueLabel')`/`t('falseLabel')` for boolean lanes). The generated `types.ts` emits `<Enum>Labels`/`<Enum>Options` next to the union type, and the form/filter bar/bulk edit/kanban/table cell/detail/dashboard chart all read them; the Java enum, CSV export and demo data keep the raw constant. Pinned by `fullstackEndpoint_rendersEnumLabels`.
- **Primary keys** — at least one PK; **composite keys** are supported (multiple `primaryKey` fields). A composite key renders a `@IdClass(<Entity>Id.class)` plus a **separate top-level** `<Entity>Id.java implements Serializable` key class (its own per-entity template `EntityId.java.mustache`, gated on `hasCompositePk` — same package as the entity, matching the standalone SQL wizard's `renderIdClass`; Lombok variant uses `@Data`/`@NoArgsConstructor`/`@AllArgsConstructor`). The repository/service/controller reference the key class directly (`{{keyClassName}}`) with a gated `import {{entityPackage}}.{{keyClassName}};`, the repository/service id type becomes the key class, and the controller addresses rows by ordered path segments `/{k1}/{k2}` (precomputed as `pkPath`). The frontend `useResource` `update`/`remove` accept an ordered key array and join it (`toPath`). A `generated` PK requires a **single** integral PK (composite + generated is rejected). `EntityScaffoldContext` exposes `pkField` (first PK, back-compat), `pkFields` (list), `hasCompositePk`, `keyClassName`, `pkType`, `pkPath`.
- **Relations** (`RelationDefinition`, `RelationType`) — **`MANY_TO_ONE`** (the FK-owning side) is what this paragraph describes and what `EntityDefinition.relations` holds; `MANY_TO_MANY` and `ONE_TO_MANY` arrived in *Round 9* and are kept in `collections` and `children`. A relation may **not** target a composite-PK entity (a single `<field>Id` can't address it — rejected). Each has `fieldName`, `targetEntity` (must be another entity in the same request — validated in a second pass and canonicalized), and `required`. Rendered as `@ManyToOne`/`@JoinColumn` (entity), a `<field>Id` component + target-entity import + a stub-by-id in `toEntity()` (DTO), a copy-on-update line (service), and an FK **`<select>`** in the frontend form (populated from the target's list endpoint `/api/<targetPlural>` via the shared `useOptions` hook; option label = target's first non-PK string field if any, else the id). When the target has a label field the entity also gets a read-only `@Formula` column `<field>Label` (a per-row subselect of the target's label column — open-in-view is off, so the DTO cannot touch the lazy association), exposed on the DTO and shown by the table/detail views (falling back to `#id`), and the CSV export. Every `MANY_TO_ONE` also becomes a **relation filter** (`filterFields` entry with `isRelationFilter`, param `<field>Id`, `root.get(field).get(pk).in(…)` — any of the ids asked for, see *Round 7*); the FE `FilterBar` renders it as a `<select>` fed by `useOptions` from the target's list endpoint. Because relations count as filters, an entity with a relation always has `hasFilters` (and the 3-arg `findAll`).
  - **Inverse `@OneToMany` collections** (opt-in `optScaffoldInverse`, derivation-only) — auto-derived from the owning `MANY_TO_ONE`s: the target parent gets a read-only `@OneToMany(mappedBy=…)` collection (no cascade), and the DTO/frontend surface a `<child>Count` (a count, never embedded child objects — avoids JSON recursion). The count is a Hibernate **`@Formula`** subselect column (`(select count(*) from <child_table> c where c.<fk_column> = <pk_column>)`, from the inverse view-model's `childTableRef`/`childJoinColumn`), **not** `collection.size()`: the DTO is built in the controller after the service transaction ended and `open-in-view` is off, so reading the lazy collection there threw `LazyInitializationException` on every `GET` of a parent entity. Soft-deleted children are still counted. Deferred: child-ID-list mode. (A wire `ONE_TO_MANY` names such a collection since *Round 9*; the DDL import derives foreign keys — see the two-pass converter below.)

#### Read-only entities & SELECT-backed views (per-entity)

Unlike the project-wide `opts.scaffold` flags, **read-only** is a **per-entity** property on `EntityDefinition` (`readOnly`, `viewQuery`; wire `EntityDefinitionDto.readOnly`/`viewQuery`). A read-only entity generates GET-only scaffolding — `EntityScaffoldContext` exposes `readOnly`, `mutable` (`!readOnly`), `isView` (`viewQuery` present), and `viewQuery`; `Service`/`Controller` wrap create/update/delete in `{{#mutable}}`, and the frontend `EntityPage` gates its New/Edit/Delete surface (the shared `Table` hides its Actions column when `onEdit`/`onDelete` are omitted).

**List views (`listViews`)** is another per-entity property (`EntityDefinition.listViews`, wire `EntityDefinitionDto.listViews`; an ordered subset of `"table"`/`"cards"`/`"kanban"`/`"calendar"`, normalized/deduped in the record's compact constructor, default `["table"]`). The generated `EntityPage` emits **exactly the enabled views** that the entity's fields support — a runtime **view toggle** appears only when 2+ are enabled, and `initialView` (the `useState` seed) is the first. The legacy single `listView` field is still accepted (treated as a one-element `listViews`) for back-compat; `EntityDefinition.listView()` returns the first enabled view. `EntityScaffoldContext` exposes the per-view flags `viewTable`/`viewCards`/`viewKanban`/`viewCalendar`, `hasViewToggle`, `initialView`, and `viewModeType` (the TS union). All view modes consume the **same `Column<T>[]` model** as `Table.tsx` (so the data/`useResource` layer is unchanged); the first column is the heading/label.

- **`cards`** — the shared `CardGrid.tsx` (responsive grid; first column is the card heading).
- **`kanban`** — the shared `KanbanBoard.tsx` (native HTML5 drag-and-drop). Lanes are the **breakdown field** (first ENUM, else BOOLEAN); dragging a card writes the new lane value back via the entity's `update`. Requested kanban is **dropped** (`viewKanban` false) when there's no breakdown field or the entity is read-only; if the resulting view set is empty it falls back to `["table"]`.
- **`calendar`** — the shared `CalendarView.tsx` (month grid). Records are bucketed by the **first temporal** (`LOCAL_DATE`/`LOCAL_DATE_TIME`) field; requested calendar is dropped (`viewCalendar` false) when the entity has no temporal field. Read-only-safe.

Independently of `listViews`, every entity with ≥1 non-PK enum/boolean/temporal/numeric field gets a **type-aware filter bar** (shared `FilterBar.tsx`, gated on `hasFilters`): enum dropdown, boolean tri-state, temporal from/to, numeric min/max. The filter values are forwarded by `useResource` as query params (`name`, `nameFrom`/`nameTo`, `nameMin`/`nameMax`) into the backend `Service`, which composes them with the text-search `Specification` (`filterFields` + `needsSpecification`). The repository already extends `JpaSpecificationExecutor`, so no repo change.

Every entity also gets a read-only **detail panel**: a row/card "view" action (`onView` on both `Table`/`CardGrid`) opens the shared `DetailDrawer.tsx` rendering the per-entity `EntityDetail.tsx` (all fields stacked, TEXT wrapped, relations/audit/inverse counts) — kept **local to `EntityPage`** (`detailRow` state) rather than threading a record id through the app's custom string-based nav. The generated **dashboard** renders a per-entity grouped **bar chart** (client-side grouping of a fetched page, no extra endpoint) for each entity whose `hasBreakdown` is set (first ENUM, else BOOLEAN field). `src/vite-env.d.ts` (`/// <reference types="vite/client" />`) makes `import.meta.env` typecheck under `tsc -b`; it is a FRONTEND `__common__` catalog row (`static-configs/frontend/common/vite-env.d.ts`), so every standalone frontend has it (auth-msal's `msal-config.ts` and the tanstack axios client read env vars — without it `GeneratedFrontendBuildSmokeTests.advertisedFeaturesProjectInstallsAndBuilds` failed), and the fullstack overlay ships the same file.

When `viewQuery` is set the entity maps to a **Hibernate `@Immutable` + `@Subselect("…")`** view instead of a `@Table` (both `Entity.java.mustache` swap on `{{#isView}}`); the field `@Column(name=…)` uses the **verbatim** field name (not snake_case) so it matches the SELECT's projected column label — so import keeps the projected alias as the field name and users control naming via `SELECT … AS alias`. A view requires ≥1 PK (the `@Id`), forbids a `generated` PK and relations, and may not be targeted by a `MANY_TO_ONE` (all enforced in `FullstackRequestValidator`, mirrored in the UI `validation.ts`).

Two import endpoints feed the editor (both `{sql, dialect?}` → wire entities): `POST /metadata/fullstack/import-ddl` (CREATE TABLE → table-backed entities) and `POST /metadata/fullstack/import-select` (a single SELECT → one read-only view; fields default to `STRING` for the user to type). The SELECT parser is `SqlEntityGenerator.parseSelectForImport`, bridged via `SqlToEntityDefinitionConverter.convertSelect` (which returns a `SelectImportResult(entities, note)`; the `note` rides back on `ImportDdlResponse`). `@Subselect` runs **native SQL**, so when JSqlParser can't parse the query, the parser falls back to a regex column extractor (`extractProjectedColumns` — finds the outer `SELECT … FROM` projection, splits on top-level commas, names each item by `AS` alias or trailing identifier) and flags `SelectProjection.heuristic`; if even that finds nothing the view comes back with zero fields for manual entry. Only a deliberate `SELECT *` / unaliased expression is a hard 400 (those parse fine — they just can't be auto-named). The standalone backend SQL wizard (`/starter-wizard.zip`) does **not** support SELECT — fullstack only for v1.

`SqlToEntityDefinitionConverter.convert` runs two passes so the DDL import keeps the schema's shape: a single-column `FOREIGN KEY` whose referenced table is in the same paste (single-key, and the FK column not itself part of the key) becomes a `MANY_TO_ONE` relation and the FK column leaves the fields (`relationFieldName`: the column minus its `_id`/`Id` suffix, camel-cased, falling back to the decapitalized target name; a still-colliding name keeps the column as a plain field). Composite FKs, FKs to tables outside the paste and FKs to composite-key tables stay plain fields. `CHECK (col IN ('A','B'))` — column- or table-level, read from the statement text with a regex because column-level checks only survive JSqlParser as raw tokens — turns the column into an `ENUM` (`toEnumConstant`: upper-case, non-identifier chars → `_`, leading digit → `_` prefix; an unsanitizable or colliding value leaves the column a string). `EntityWire` carries `relations`. The validator's enum-constant keyword check is exact-case (`NEW`/`DEFAULT` are ordinary constants; a literal `new` is rejected). Pinned by `SqlToEntityDefinitionConverterTest` and `importDdlEndpoint_turnsForeignKeysIntoRelationsAndCheckInIntoEnums`.

**Column names survive the import.** Every imported field carries `column` and every relation `joinColumn` (`FieldDefinition.column`, `RelationDefinition.joinColumn`, both optional on the wire and in the editor's "DB column" / "Join column" inputs) holding the name exactly as the DDL spells it, because camel-casing is lossy: `FRF_QOD_MISHLOAH_FUTURE_USE_8` → `frfQodMishloahFutureUse8` → snake-cases back to `…_use8`, and an FK without an `_id` suffix (`CUST_REF`) would derive `cust_ref_id`. `EntityScaffoldContext.columnOf`/`joinColumnOf` resolve them (explicit name, else the old derivation — so requests without them keep their bytes) for `@Column`, `@JoinColumn`, the soft-delete SQL, the relation-label and child-count `@Formula`s. The validator allows only `[A-Za-z_][A-Za-z0-9_$#@]{0,127}` (they are spliced into native SQL), rejects a `column` on a view, and 400s when an explicit name lands on a column another member already maps to (`checkColumnClashes`). The standalone SQL wizard never had the problem — it writes `@Column(name = "<ddl name>")` whenever the field name differs. **Mixed-case and quoted names (`sql/SqlNames`).** Boot's default `CamelCaseToUnderscoresNamingStrategy` rewrites *every* table/column name — explicit and quoted ones included (`orderDate` → `order_date`, `"OrderDate"` → `"order_date"`) — while native SQL is left alone. So both generators render each DDL name through `SqlNames.physical(name, quotedInDdl, dialect)`: an unquoted name the strategy would split (a lower-UPPER-lower hump) becomes upper case (DB2/Oracle/H2 fold to it; PostgreSQL's lower-case fold is what the strategy's lower-casing produces), quoted on SQL Server, and quoted on MySQL whenever it has an upper-case letter (table names are case-sensitive there); a name the DDL quoted keeps its quotes in the dialect's style unless it is what the database stores for the bare name anyway (`"ORD_NO"` on DB2 — db2look quotes everything). The parser records quoted names per table (`TableModel.quotedNames`, `TableModel.physical`). The fullstack import stores the result in `column`/`joinColumn`/`tableName`/`schema`; the renderer (`columnOf`/`joinColumnOf`/`tableOf`/`schemaOf`/`tableRefOf`) passes stored names through `SqlNames.physical(stored, null)` again (a hand-typed `orderDate` folds too) and Java-escapes them (`SqlNames.javaLiteral`), and a SELECT view maps fields through `viewColumn` (a camelCase alias folded). Any quoted name makes the project ship `config/QuotedNamesNamingStrategy` (`SqlNames.namingStrategySource`: Boot's strategy, except quoted identifiers pass through; a `@Component`, which Boot picks up as the `PhysicalNamingStrategy`) — written by `SqlEntityGenerator.generate` and by `FullstackProjectGenerationConfiguration` from Java, not a template row, so upgraded DBs get it too. The native soft-delete SQL now uses the schema-qualified `tableRef`. The validator's `SQL_NAME` accepts plain names and `"x"`/`` `x` ``/`[x]`, and now also checks `tableName`/`schema`. Pinned by `SqlNamesTest`, `SqlEntityGeneratorTest.postgresql_mixedCaseNamesSurviveTheNamingStrategy`/`db2_quoteEverythingExportNeedsNoNamingStrategy`, `importedDdl_keepsMixedCaseAndQuotedNamesThroughTheNamingStrategy` and `fullstackEndpoint_mapsCamelCaseViewAliasesThroughTheNamingStrategy`. Earlier pins: `fieldsAndRelationsKeepTheirDdlColumnNames`, `importedDdl_generatesEntitiesOnTheSchemasOwnColumnNames`, `fullstackEndpoint_rejectsBadOrClashingColumnNames` and `SqlEntityGeneratorTest.db2_keepsAnUnderscoreBeforeADigitInTheColumnName`.

  - `validation` — `NOT NULL` → `@NotNull` (never on a key the database generates), a text column's length → `@Size(max)`, a required foreign key → a required id; on the DTO, or on the entity when it is exposed directly (`ENTITY_DIRECT`); controllers take `@Valid` bodies. Without the starter nothing names `jakarta.validation`.
  - `sqlOptions.<dep>.generateTests: true` — a `@WebMvcTest` per controller (`templates/wizard/sql/ControllerTest.java`; `@MockitoBean` from Boot 3.4).
- *OpenAPI: schemas* (`openapi/SchemaRecordEmitter`, `SchemaSet` — one per document, built with the DTO package and whether validation is on; `typeOf(schema, hint)` is the only type mapping):
  - a string `enum` → a Java enum that keeps each wire value (`@JsonValue`/`@JsonCreator`, `Enum.java`); written in a property it is named after its place (`Pet.status` → `PetStatus`). A **parameter** of an enum type stays `String`: Spring binds an enum by its constant's name, and `in-progress` cannot be one;
  - `allOf` → one merged record (it was an empty record with a TODO);
  - `oneOf`/`anyOf` over object schemas → a sealed interface (`Union.java`): `@JsonTypeInfo` by the discriminator (its `mapping` honoured; `EXISTING_PROPERTY` when every member declares the property) or `DEDUCTION` without one. Each member record carries `@JsonTypeInfo(use = NONE)`, so it is still read on its own — otherwise `{"id": 1}` asked for as a `Pet` failed as "cannot deduce". A choice between non-objects stays `Object` (the plan said 400; one exotic schema should not refuse a whole document);
  - a named schema that is not an object (a string with a format, an array, a map, a free-form object) is **not a type**: a reference to it is the type it stands for, constraints included (it used to be an empty record). `additionalProperties` → `Map<String, V>`; an object written in place → a record named after its place (a request body: `<Operation>Request`, a response: `<Operation>Response`);
  - a property whose Java name differs from its name on the wire gets `@JsonProperty` (`first_name` was read and written as `firstName`); a keyword is suffixed (`class_`). A schema named like a type the generated code uses (`List`, `Valid`, `HttpStatus`…) is renamed `<Name>Dto` (`RESERVED_TYPE_NAMES`);
  - `date-time` → `OffsetDateTime`; OpenAPI 3.1's `type: [string, 'null']` is read (`typeName`);
  - with the validation starter: `@NotNull` (required and not nullable), `@Size`, `@Pattern`, `@Email`, `@Min`/`@Max`, `@DecimalMin`/`@DecimalMax`, `@Valid` on nested types — on record components and on controller parameters (`constraintsOf`).
- *OpenAPI: operations.* Parameters are bound by the request's names (`ParamModel.wireName`): `X-Request-Id` was bound as `xRequestId`, so the header never arrived. A cookie is `@CookieValue` (it was `@RequestParam`). Date parameters carry `@DateTimeFormat(iso = …)` (Spring otherwise reads the server locale's short style). Path-level parameters are read. The declared success status — the lowest 2xx, then `2XX`, then `default` — is a `@ResponseStatus` where it is not 200, and decides the return type (a 204 used to lose to `default`, so a delete returned the error body's type). HEAD and OPTIONS are generated. A body is optional only when the document says `required: false`. Clients send the same names, expand path variables in the **path's** order, and use `fromUriString`.
- *OpenAPI: options.* `openApiOptions.<dep>.clientKind`: `restTemplate` (default) or `restClient` (`RestClientClient.java`, `RestClientConfig.java`; unknown → 400). `copySpec: true` keeps the document at `src/main/resources/openapi/<dep>.yaml|json` (written by the contributor).
- *The starters a wizard's code needs are added* (`WizardStarterController.toWebRequest`, only when the catalog has them — `ProjectRequestFactory.offers`): `web` for an OpenAPI payload without `web`/`webflux`, `openapi` (springdoc) beside generated controllers on `web`, `web-services` for a WSDL.
- *OpenAPI, built:* `openApiWizardBackendCompilesAndItsContractBehaves` (controllers + RestTemplate client + validation) and `openApiWizardRestClientCompilesAndCallsTheContract` build the Petstore fixture and run `OPENAPI_CONTRACT_TESTS` / `OPENAPI_REST_CLIENT_TESTS` inside the generated project: JSON round trips of the union, the enums and the renamed properties, the constraints through a `Validator`, controller binding through MockMvc (a bound call reaches the stub's `UnsupportedOperationException`), and each client against a `MockRestServiceServer`. **Add a method there for anything about generated wizard code a text assertion cannot prove.**
- *SOAP.* A WSDL that refers to another file — `wsdl:import`, or `xsd:import`/`include`/`redefine` with a `schemaLocation` — is a 400 naming each reference (`unresolvedImports`, on generate and on the preview). It is found by scanning the document **before** wsdl4j parses it, with a parser that takes no DOCTYPE: wsdl4j's reader opens a `schemaLocation` itself, relative to the server's working directory or by URL. An `xsd:import` of a namespace alone is fine. Multi-file WSDLs remain unsupported.
- *Not done from the plan:* a shared `SqlConstraintReader` (the fullstack DDL import keeps its own CHECK/FK reading in `SqlToEntityDefinitionConverter`; both read the same `TableModel`); multipart/form request bodies (still `@RequestBody` over the first media type); a real build of SOAP output (the JAX-WS plugin's artifacts are not known to be in the offline repository).

Pinned by `SqlEntityGeneratorTest` (63 cases), `OpenApiCodeGeneratorTest`, `SoapCodeGeneratorTest`, `ProjectGenerationIntegrationTests.wizardsAddTheStartersTheirCodeNeeds` / `sqlWizardRefusesAnUnknownApiMode` and 21 wizard golden manifests.

**Round 10, phase 4: the events wizard (AsyncAPI → Kafka).** A fourth wizard on `/starter-wizard.zip`, keyed by the `kafka` dependency. No existing manifest moved.

- *Wire.* `asyncApiByDep: {kafka: "<document>"}` and `eventOptions: {kafka: {subPackage?, payloadSubPackage?, groupId?, channels?: [{name, produce, consume}], generateTests?}}` on `WizardStarterRequest`. `POST /starter-wizard.detect-channels {spec}` → `[{name, address, sends, receives, messages, problem}]` for the drawer (400 `{error: "Invalid AsyncAPI document", messages}` for a document that cannot be used — the same body generation answers). `GET /metadata/events-capable-deps` → `["kafka"]`. `kafka` is added to the build when the caller named no such dependency.
- *Reading (`events/AsyncApiReader`).* 2.x and 3.x, YAML or JSON, read as a tree — there is no AsyncAPI library in the offline repository, and the wizard needs little of the specification. **The two versions say who sends in opposite words:** 2.x's `publish`/`subscribe` are a *client's* (what clients subscribe to, the application sends); 3.x's operations say `send`/`receive` from the application's own side. Both come out as `EventChannel.sends()`/`receives()` — what the described application does. A channel's `name` is its key under `channels`; its `address` is 3.x's `address` (else the key), 2.x's key. Messages: 2.x `message` or `message.oneOf`; 3.x the channel's `messages`, limited to those an operation lists. Refused, each with its reason: no `asyncapi` field, a version other than 2.x/3.x, no channels, a `schemaFormat` that is not JSON Schema (AsyncAPI's own, JSON Schema, OpenAPI — so Avro is a 400), a `$ref` out of the document or into nothing. A parameterized address (`users.{id}.inbox`) cannot be a Kafka topic: the channel carries a `problem`, is left out by default and is a 400 when asked for.
- *Which channels (`EventsCodeGenerator.plan`).* No `channels` in the options: the project **is the application the document describes** — a producer where it sends, a listener where it receives. With `channels`, exactly those, in the directions given (that is how the other party is generated; `{produce: false, consume: false}` leaves one out). An unknown name, a name twice, or nothing left to generate is a 400 (`WizardArgumentException`).
- *What is written* (`templates/wizard/events/{Producer,Listener,ProducerTest,ListenerTest}.java`, default packages `events` and `events.model`):
  - `<Channel>Producer` — `send(String key, <Payload> payload)` over `KafkaTemplate<String, String>`; several kinds of message on one channel give a method each (`send<Message>`).
  - `<Channel>Listener` — `@KafkaListener`, reads the payload and calls `handle(key, payload)`, a stub. Several kinds of message: nothing in a record says which, so it is handed the `JsonNode`. `groupId` is the option, else `${spring.kafka.consumer.group-id}`.
  - **Messages travel as JSON text.** The catalog's Kafka dependency configures `KafkaTemplate<String, String>` and String (de)serializers (`KafkaConfig`, `application-kafka.yml`); that is left alone, and the generated classes convert with the application's `ObjectMapper`. `eventsBuildCustomizer` adds `spring-boot-starter-json`, since a project with Kafka and no web starter has neither Jackson nor that bean.
  - A topic's name is a property, `app.events.topics.<channel-in-kebab-case>`, set to the channel's address in `application.yaml` (merged).
  - The payload types are the OpenAPI wizard's. Payload schemas are JSON Schema, which is what an OpenAPI 3.1 document's schemas are: `Payloads` puts the document's `components.schemas` — and each payload written in place, under its message's name — into a synthetic 3.1 document, parses it with swagger-parser and reads it with `SchemaRecordEmitter.read`. **A change to the type mapping there reaches both wizards.** Every schema the document names becomes a type, used by a chosen channel or not.
  - `generateTests`: per producer, the payload out through a mocked `KafkaTemplate` and back from the JSON; per listener, a record in. No broker. A test value is made where one is simple (`sampleOf`: a record with every component null, an enum's first constant, an empty list…); a union payload gets no round-trip test.
- *Plumbing.* `config/EventsSpecContext` is the **sixth** per-request ThreadLocal context: populated in `WizardStarterController.populateContexts`, cleared in its `finally` and by the `InitializrWebConfiguration` backstop (`GenerationContextCleanupTests` covers six). `validateEvents` runs the generator once before generation, so every refusal is a 400, never a half-written project. `eventsCodeContributor` (`@Order(100)`) writes the files.
- *Built for real:* `GeneratedBackendBuildSmokeTests.eventsWizardBackendCompilesAndPassesItsTests` — every channel of the 3.x fixture in both directions, with validation and the generated tests: the project compiles, its tests pass, its context starts (no broker is needed for that).
- *Limits.* Kafka only (the document's own bindings and servers are not read). JSON payloads only. Message headers, keys' schemas, correlation ids and traits are not read. A reference from inside a payload to somewhere other than `#/components/schemas/…` is not followed.

Pinned by `EventsCodeGeneratorTest` (the two fixtures, `wizard-fixtures/orders-asyncapi-v{2,3}.yaml`, describe the same events), `ProjectGenerationIntegrationTests.eventsWizard*` and two golden cases (23 wizard manifests).

**Round 10, phase 5: plain backends keep their model, and are updated from it.** What fullstack projects have had since Rounds 6 and 9, for `/starter.zip`, the wizards and multi-module projects. Every plain, wizard and multi-module golden case changed, deliberately; no fullstack manifest moved.

- *The model file (`config/BackendModel`).* `menora-model.json` at the project's root: `{format: "menora-backend-model/1", kind: "backend" | "multimodule", request, generator: {catalogHash}}`. `request` is a `/starter-wizard.zip` body (plus `modules` for a multi-module project) **as the generation resolved it** — the starters a wizard added, the datasource roles defaulted, each wizard's document with its options written back from the parsed record (`BackendModel.wire`: Jackson over the options records, whose component names are the wire names). Generating a model's own `request` gives the same bytes (pinned).
- *Who writes it.* `backendModelContributor` in `DynamicProjectGenerationConfiguration` (`@Order(LOWEST_PRECEDENCE)`), from the `ProjectDescription` and the per-request contexts — **not the endpoints**: `/starter.zip` is the framework's own controller, and its output has to stay byte for byte what `/starter-wizard.zip` generates without a wizard (still pinned by `WizardGoldenOutputTests`). The same contributor prepends `* text=auto eol=lf` to the framework's `.gitattributes` (`BackendModel.gitAttributes`) and normalizes every text file to LF — a patch made from generated files met CRLF ones on a Windows checkout. `modelHelpCustomizer` (a framework `HelpDocumentCustomizer`) adds *Reopening and updating this project* to `HELP.md`.
- *A project that is part of a larger one writes none.* `ProjectOptionsContext.setEmbedded(true)` — set by `FullstackStarterController` before it generates its backend (the fullstack root has its own model) and by `MultiModuleController.assemble` around its modules — makes the contributor and the help section stand down. A multi-module project gets one model at its root (`MultiModuleController.modelOf`: the root's coordinates, `modules` = the templates that exist, in their order, `dependencies` = what every module was given beside its own) and a root `.gitattributes`. `ProjectOptionsContext.all()` is every selected sub-option as it stands; `clear()` resets the flag.
- *`POST /starter.patch` (`config/BackendPatchController`).* `{base, target, baseCatalogHash?}`; each side is a model file as it is, or just its `request`. A request with `modules` is assembled by `MultiModuleController.assembleModel`, any other generated by `WizardStarterController.generateProject` (the wizard endpoint's own pipeline, contexts cleared after each side). The difference comes back as `<artifact>-update.zip` from `ProjectUpdateBuilder` — the fullstack update's machinery; its `Info` now also carries the project's root in words and what the hashes are of ("templates" / "catalog"), with the fullstack notes word for word what they were. `menora-model.json` is replaced whole, never patched. A model that cannot be generated is a 400 `{error: "Invalid model", side: "base" | "target", detail, messages}`.
- *`generator.catalogHash`.* `BackendModel.catalogHash`: the SHA-256 of the file contributions and build customizations **of the model's own dependencies** (in a fixed order, line endings aside). Because it covers only those rows, an update compares the hash the project was generated with (the caller's `baseCatalogHash`, else the base model file's) with the hash of **the base model generated today** — not the target's, whose dependencies may differ — and says in `UPDATE.md` whether the catalog moved. As with fullstack, the patch is the change the *model* makes: both sides are generated with today's catalog.
- *Limits.* The model records the request, not the catalog: an update does not bring catalog changes. Sub-options of a multi-module project are recorded for the dependencies its modules use. `/starter.zip` answers with no header naming the hash, so a project generated in the editor (not imported) has no "generated with" hash until its file is imported.

Pinned by `BackendPatchTests` — the model and its round trip (wizard, `/starter.zip`, multi-module), the update zip and its notes, the 400s, and the whole journey with real git (generate, commit, edit by hand, change the model, `git apply --3way`).

**Round 10, phase 6: composition — child rows edited in their parent's form.** What Round 9 cut. Gated throughout: a request without a composition keeps its bytes (no fullstack manifest moved until the Orders example was given one).

- *Wire.* `composition: true` on a `ONE_TO_MANY` relation (`RelationDefinitionDto.composition`, `RelationDefinition.composition`). The rows of the target are then **part of this entity**: its form edits them, a save carries them, a row left out of a save is removed.
- *What may be composed (`FullstackRequestValidator.checkComposition`, run where the link behind the list is settled; each a 400 at `…relations[i].composition` that says which rule).* Only a ONE_TO_MANY; never an entity's own rows; the parent writable; the child writable, with a **single generated key** (a new row has no id — that is how it is told from a kept one), its link to the parent **required**, no workflow, no FILE/IMAGE field, no MANY_TO_MANY or ONE_TO_MANY of its own; and one owner per child.
- *Backend (`hasCompositions` on the parent, `isComposedChild` on the child; both backend sets).*
  - Parent entity: `@OneToMany(mappedBy, cascade = {PERSIST, MERGE, REMOVE})` — **without `REMOVE` when the parent is soft-deleted** (`cascadeJava`, from `softDeleteApplicable`): a row deleted softly can be restored, so its rows stay. No `orphanRemoval`: a removed row is deleted explicitly, so the two cases share one code path.
  - Parent DTO: `List<ChildDto> <list>` (`@Valid` with the validation starter — a row's message is keyed `lines[0].quantity`). `from()` fills it only where the collection is initialized (`Hibernate.isInitialized`), which the service does for **one row read by id** (`withRows`) — a page of rows carries `null`. `toEntity()`: no list at all is `null`, meaning "leave the rows as they are" to an update.
  - Parent service: `create` adopts the rows (`adopt<List>`: the row's link is the parent, its key is the database's, its other foreign keys become managed references — `childRefs`); `update` merges (`merge<List>`): a row with the id of a row the parent has is that row with its new values (`Child.copyFrom`), any other is new — **an id that is not one of this parent's rows is never trusted** — and a row not sent is removed. At most `MAX_ROWS` (200) rows in one save. Under optimistic locking a change to the rows force-increments the parent's version. A CSV import and the bulk and inline edits carry no rows.
  - Child: `copyFrom(other)` on the entity (its values and foreign keys, never its key or its parent); the DTO no longer requires the link (`dtoRequired` — inside its parent a row need not say whose it is), and the child's own `create` (and import) asks for it instead. The child's own endpoints and page are unchanged.
- *Frontend (both sets; new files, and small gated blocks in the form, the types, the validator, the wizard and each set's `EntityPage`).* `shared/ui/RowsEditor.tsx` (ships with `hasCompositionRows`): a small table with an input per cell, add and remove. Per composed child, `features/<child>-form/ui/<Child>Rows.tsx` (`EntityRows.tsx.mustache`, gated `isComposedChild`; `putRows`): a column per value a client may set and per foreign key but the link to the parent, a `RelationPicker` or a select per link. The parent's form renders it after its fields; `types.ts` gains `<list>?: Partial<Child>[] | null`; `validate<Parent>` runs `validate<Child>(row, true)` on every row (the `nested` flag skips the link) and keys the messages by place, which is where the server's land too. A row of a list has no rows of its own, so `EntityPage.openEdit` reads the record by id and merges the lists into the open form (a save before they arrive leaves them alone). A wizard gets a step per composed list after its own (`wizardHasRows`; the step owns every message under the list). Form pages and the record page's Edit read the record by id already.
- *Example.* Orders: `Order.lines` is a composition.
- *Limits.* One level (a composed child composes nothing). The rows are replaced as a set by whoever saves last unless the parent is versioned. No paging inside the form: 200 rows. The details still show the rows read-only (`RelatedRows`). The editor's canvas does not draw the rows editor or the wizard's extra step.

Pinned by `FullstackCompositionTests` (both backend shapes, both frontend sets, every 400) and `ReservedNamesGuardTest` (`RowsEditor`, `RowColumn` are reserved entity names now). Driven for real by `GeneratedBackendBuildSmokeTests.liveApiOfAComposedParentBehaves` (both backend sets, with soft delete and locking: rows saved, read, changed, removed, checked by place, never taken from another parent, kept through a soft delete) and built by `GeneratedFrontendBuildSmokeTests.fullstackFrontend*Composition*` (Orders layout on tailwind, classic Hebrew on Menora).

**Round 10, phase 7: rich fields and output.** An Excel export, an editor for Markdown fields, pictures on cards, a drop zone on the attachment field and printable record pages. Each is gated; the manifests that moved are the examples that were given the feature (Orders: the Excel option; Blog: `Post.body` is MARKDOWN; Approvals: the claim page prints) and Approvals again for the attachment field, which every project with a FILE or IMAGE field ships.

- *Excel export (`xlsxExport`, a `ScaffoldOption`, per entity like `csvExport`).* `GET /api/x/export.xlsx` beside the CSV endpoint — **the same parameters, copied from it** (`q`, the filters, `sort`, a workflow's `inbox` and user), so the workbook is the list on screen; the CSV endpoint's bytes are untouched.
  - `web/XlsxWriter` (`XlsxWriter.java.mustache`, gated on the project flag `hasXlsxExport` = any entity resolving the option on — `EntityScaffoldContext.putXlsxExport`, both render paths; the Lombok set borrows it). **No library**: an `.xlsx` is a zip of XML parts, written straight to the response with `ZipOutputStream` — five fixed parts, then the sheet, streamed row by row in the 500-row chunks the CSV export reads. Apache POI was decided against (a large dependency in every generated backend, for one sheet of cells).
  - Cells: a `Number` is a number cell, a `Boolean` a boolean, everything else **inline text** (`t="inlineStr"`), dates and enums included (ISO text and the constant, as in the CSV). Text is never a formula in SpreadsheetML unless it is written as one, so the CSV's apostrophe guard is not needed and not applied. The header row is bold (`styles.xml`, one extra font). A sheet name loses the characters Excel forbids and is cut to 31.
  - Columns (`putXlsxColumns` → `xlsxHeaders`, `xlsxCells`, `xlsxSheetName`, built in `buildEntityContext` only when the entity's option is on): every DTO value under **the label the UI gives it**, Java-escaped (`SqlNames.javaLiteral`) — a foreign key by the row it points at where that row has a name (`<field>Label`, else the id), a file by its name, a many-to-many by its names joined with `; `, the audit pair last. The cell expressions are Java built in Java; the template only lists them.
  - Frontend (both sets' `EntityPage`): an **Excel** button beside Export. The page builds the query itself from its `debouncedSearch`, `filters` and `sort` and downloads through `api.download` (imported as `sheetApi`, gated) — `useResource` keeps its bytes. `usesDownload` (CSV ∨ Excel) gates the one `useDownload` busy flag. Strings `exportXlsx`/`excel` on `hasXlsxExport`.
  - Either export counts as "an action to hide" for a list page's `hideActions` (`FullstackPageValidator.listSpec`, `listActionsConfigurable`); the `export` action hides both buttons.
- *Markdown editor.* A MARKDOWN field's form control is `shared/ui/MarkdownEditor.tsx` (ships with `hasMarkdownFields`, borrowed by the Menora set; the form imports it on the per-entity `hasMarkdownField`) instead of a bare textarea: Write / Preview, eight buttons (bold, italic, heading, bulleted and numbered list, callout, link, code — exactly the subset `Markdown.tsx` reads) and Ctrl+B / I / K. A line button toggles. **The preview is `Markdown.tsx` itself**, the component the details show the value with, so nothing typed is ever markup here either. A composed child's rows editor still takes long text in a plain input.
- *Pictures on cards.* `displayTs(IMAGE, …, Display.CARD)` is a 40px thumbnail (it was the file's name), so a board card and an inbox row show an IMAGE field as the table already did; `putCardFormatImports` imports `attachmentUrl` for it. A FILE on a card is still its name.
- *Attachment field.* `AttachmentField.tsx` takes a file **dropped** onto it (only a drag that carries files; an image field refuses another type before sending), shows the picked picture from the browser's own copy while it uploads, and says `dropHere` beside the button.
- *Printable record pages.* `printable: true` on a `record` page (`PageDefinitionDto.printable`, `PageDefinition.RecordSpec`; on another type a 400; absent and false are the same bytes). The screen gets a **Print** button (`window.print()`) and `print:hidden` on its own controls (back, previous/next, actions, the tab strip); the project flag `hasPrintablePages` appends an `@media print` block to both sets' `index.css.mustache`: the shell's scrolling, window-high boxes become ordinary flow (otherwise paper shows one sheet), and `aside`, `header`, `footer`, `nav`, dialogs and toasts are not printed. What prints is what the page shows — the open tab. **`PageDefinitionDto` has a chain of older constructors:** a new property goes on the canonical one, and only the constructors that call the canonical one pass a `null` more.
- *Limits.* The workbook has one sheet, no column widths, no date cells (ISO text sorts and filters correctly, but is not a date to Excel) and no composed rows. Print styles cover record pages only.

Pinned by `FullstackXlsxExportTests` and `FullstackRichFieldsTests`. ### Adding or Modifying a Dependency

The DB is the source of truth. Use the admin API at runtime, or edit the catalog manifests for the initial seed:

1. **New dependency** — POST to `/admin/dependency-groups` + `/admin/dependency-entries`
2. **New file to inject** — POST to `/admin/file-contributions` with `dependencyId`, `fileType`, `content`, `targetPath`
3. **New build customization** — POST to `/admin/build-customizations`
4. **Hot-reload** — POST to `/admin/refresh` (no restart needed)

For a permanent change that survives a fresh DB (e.g. new deployment), edit the relevant manifest under `src/main/resources/catalog/` (drop any new content file under `static-configs/`/`templates/` and reference it via `contentResource`). See the catalog-manifest table above.

### Sub-Options (Optional Per-Dependency Files)

Some dependencies expose sub-options selectable by the user (e.g. `consumer-example`, `producer-example` for Kafka). URL convention: `opts-{depId}=opt1,opt2`.

`InitializrWebConfiguration` (the `@Order(MIN_VALUE)` servlet filter) calls `ProjectOptionsContext.populate(request)` before generation and `clear()` after. `DynamicProjectGenerationConfiguration` checks `optionsContext.hasOption(depId, subOptionId)` before writing sub-option-gated files.

Sub-options are managed via `/admin/sub-options`.

### Dependency Catalog in Metadata

`DatabaseInitializrMetadataProvider` (`@Primary` bean via `MetadataProviderConfig`) loads the dependency catalog from the DB. Non-dependency metadata (Java versions, Boot versions, packaging, types) still comes from `application.yml`.

The provider caches the metadata. Call `POST /admin/refresh` to invalidate the cache after DB changes.

`DependencyConfigService.getAllGroupsWithEntries(kind)` returns `GroupEntries(group, entries)`, with the group's entries of that kind filtered into a **new** list. Admin writes rebuild the metadata inside their own transaction, and `DependencyGroupEntity.entries` is an orphanRemoval collection. The rebuild used to `removeIf` cross-kind rows from it, which deleted them from the database whenever groups were reordered. Never mutate that collection on a read path. This is pinned by `GroupReorderKeepsCrossKindEntriesTests`.

A dependency that fails to build (bad `compatibilityRange`, bad `scope`, …) is skipped rather than taking the catalog down, but it then silently vanishes from `/metadata/client`. The skipped rows are recorded in `DatabaseInitializrMetadataProvider.getLoadFailures()` and returned by `/admin/refresh` as `{"message": …, "failed": […]}`; the admin UI shows them as an error toast.

### Dependency Version Compatibility Ranges

Each `DependencyEntryEntity` has an optional `compatibilityRange` field (column: `compatibility_range`). When set, the Spring Initializr framework automatically:

- Excludes the dependency from `/metadata/client` responses when the selected Boot version falls outside the range
- Includes `"versionRange"` in the metadata JSON for clients to display

**Range syntax** (interval notation):
- `[3.2.0,4.0.0)` — Boot ≥ 3.2.0 and < 4.0.0 (most common)
- `3.2.0` — Boot ≥ 3.2.0 (open upper bound)
- `[3.2.0,3.3.0]` — inclusive on both ends

A blank/null range means the dependency is compatible with all Boot versions (default behavior).

Set via the admin UI (Dependencies tab → edit → Compatibility Range field) or in `catalog/dependencies.json` (the `compatibilityRange` field on an entry) for fresh-DB seeds. The range is validated by `dep.resolve()` at metadata-build time — a malformed range throws immediately on refresh.

### Request performance

- **Open-in-view is off** (`spring.jpa.open-in-view: false`), so a generation no longer holds a pooled
  connection from its first query through rendering and zipping. The admin API still needs it — its endpoints
  return entities whose lazy `group`/`template`/`entries` Jackson reads — so `admin/AdminOpenEntityManagerConfig`
  registers the interceptor for `/admin/**` only. A new non-admin endpoint must return DTOs or fetch what it
  serializes.
- **Responses are gzipped** (`server.compression`, JSON + the Initializr media types, ≥ 2 KB): a fullstack preview
  shrinks ~5×. Tomcat skips responses with a strong ETag (`/metadata/client`), by design.
- **`config/CompiledTemplates`** is the one Mustache compiler (`escapeHTML=false`) with an LRU of compiled
  templates keyed by text — every generator renders through `CompiledTemplates.render`; don't add another
  `Mustache.compiler()`. `FullstackRenderer` builds each entity's context once per render, not once per file.
- **Generation is mostly filesystem time**, so `GeneratedProjectFiles` has `moveDirectory` (the fullstack/multi-module
  backend is renamed into place, not copied), `deleteLater` (temp trees are deleted on a background thread after
  the response; the framework's own `invoker.cleanTempFiles` stays synchronous) and `createParentDirectories`
  (one `isDirectory` check instead of `createDirectories`' failed create per file).
- The metadata is built on `ApplicationReadyEvent` (`MetadataProviderConfig.warmMetadata`), the team-model list
  reads a projection without the snapshot column, and `/metadata/starter-templates` / `entity-template-sets` load
  their child rows in one query.

### Per-Request ThreadLocal Contexts

Six `@Component` holders in `config/` carry per-request state into the generation child
context: `ProjectOptionsContext`, `SqlScriptsContext`, `OpenApiSpecContext`, `SoapSpecContext`,
`EventsSpecContext` (Round 10), `EntityDefinitionContext`. Controllers populate what they need **inside** their `try` and clear
it in the `finally`, but `InitializrWebConfiguration` (the `@Order(MIN_VALUE)` filter) clears
**all six** in its own `finally` as the unconditional backstop — no controller covers every
context, and an exception reaching `GlobalExceptionHandler` clears none. Without that backstop a
leftover context gets scaffolded into the next request served by the same pooled Tomcat thread.
Pinned by `config/GenerationContextCleanupTests`.

### Test Infrastructure

Tests use `src/test/resources/application.properties` which configures an in-memory H2 (`ddl-auto: validate`, schema managed by Flyway; `admin.password=test`). `DataSeeder` runs automatically at test startup and seeds the DB from the catalog manifests, so tests exercise the full DB-driven pipeline.

**Always release an invoker-generated directory with `invoker.cleanTempFiles(dir)`, not `FileSystemUtils.deleteRecursively(dir)`.** `ProjectGenerationInvoker` is a singleton bean that registers every generated root in a private `temporaryFiles` map and only drops the entry in `cleanTempFiles` — a plain delete removes the files but leaks the map entry for the life of the JVM. `cleanTempFiles` deletes the tree too, so it replaces the delete rather than joining it. It only accepts paths the invoker produced (it NPEs on an unknown path), so directories from `Files.createTempDirectory` still use `FileSystemUtils.deleteRecursively`. Pinned by `InvokerTempFileCleanupTests`.

**Catalog sync (`db/CatalogSync`, 2026-11): file contributions and build customizations follow the release.** The fullstack template sets have followed the shipped files since Round 9; the dependency catalog's files (Dockerfiles, nginx, datasource configs, the Vault rows) and build rows (BOMs, added and excluded dependencies) were seeded once, so every fix to one reached new databases only — the "upgraded databases keep the old rows" lines above. They follow now. Dependency groups and entries, sub-options and compatibility rules are **not** part of it: still seeded once.

- *What is remembered.* `initializer_catalog_seed` (`V28`, `CatalogSeedEntity`): one record per row a release ships — `seed_key` (sha256 of the row's identity), `applied_hash` (fingerprint of the shipped version last written to this database, null when it never was), `kept`. A table of its own rather than a `seed_hash` column on the two catalog tables, because **a deleted row has to be remembered too** — the template sync puts a deleted file back on the next start; this does not.
- *Identity and fingerprint.* A file row is the same row from one release to the next by kind, dependency, target path, sub-option, Java version and Node version; a build row by kind, dependency, type, group and artifact, repository id, sub-option and Boot range (`CatalogSync.keyOf`; each is unique over the shipped manifests, pinned). Everything else is the fingerprint: content (line endings normalized, like the template sync), file type, substitution type (null = `NONE`, what the admin form saves) and sort order; version, exclusions, repository name and URL, snapshots, scope and sort order. An admin who changes an identity field has made another row: the shipped one counts as deleted.
- *On start* (`CatalogSync.sync`, called by `DataSeeder` — after seeding a fresh database, where every row is recorded as in step, or on an existing one), per shipped row: the stored row still has the fingerprint last applied → rewritten to the release's (**updated**); it has another → left alone (**differs**); there is no stored row but one was applied here before → an admin deleted it, left alone; the release ships it to this database for the first time → **added**. A record whose row the release no longer ships: the row is removed when it still has the applied fingerprint, kept otherwise, and the record goes either way.
- *The baseline: the first start of an existing database.* Nothing is recorded, so a row that differs may be an admin's edit or an older release's content, and a missing one may have been deleted or never there. **That start changes nothing**: it records every shipped row — in step where the stored one matches, never-applied where it differs or is missing — and logs one warning with the two counts. This was a choice (the template sync overwrote such rows once): an admin's edits to a Dockerfile are not ours to lose.
- *For the admin* (`admin/CatalogSyncController`, behind the admin login; there is no screen yet): `GET /admin/catalog-sync` → `{enabled, summary, rows: [{key, table, kind, dependencyId, label, status, rowId}]}` with `status` one of `IN_STEP`, `DIFFERS`, `MISSING` (never applied and absent), `KEPT`, `DELETED` — `?status=DIFFERS,MISSING` narrows the rows; `GET /admin/catalog-sync/{key}` → `{row, shipped, current}`, the two entities side by side for a diff; `POST /admin/catalog-sync/apply` `{keys: […]}` takes the shipped version of those rows (rewritten in place, a missing one added) and `{all: true}` of every row that differs or is missing — never one an admin kept or deleted, those are named to be taken; `POST /admin/catalog-sync/keep` `{keys: […], kept?: false}` marks rows as the admin's own (no longer reported, never replaced), or undoes it.
- *Switch.* `initializr.catalog.sync=off` leaves the catalog alone (a fresh database is still seeded).
- *The admin import* (`/admin/import`) replaces the catalog's rows and leaves these records: an imported row that equals what was last applied keeps following, any other is reported as differing.
- *Tried on a copy of a real database* (seeded several rounds ago): 311 rows in step, 10 differing, none missing — the five `*-config-primary` datasource templates (Round 10, phase 1), the three frontend Dockerfiles (Round 9) and Round 12's `nginx.conf` and `entrypoint.sh`. `apply {all: true}` wrote the ten.

*Limits.* A row saved from the admin form without a change counts as edited if the form alters anything beyond line endings and a missing substitution type. Two instances starting at once on one database both run the sync; there is no lock. Several stored rows with one identity (an admin's copy): the one equal to the shipped row is taken for it, else the first.

Pinned by `CatalogSyncTest` (each rule; "the release moved on" is staged by giving a row other content and recording that content as applied) and `CatalogSyncAdminTests` (the endpoints).

**Fullstack migrations (`fullstack/schema/`, 2026-11): with Flyway, the entity model is the first migration.** A fullstack project on PostgreSQL, Oracle, SQL Server or DB2 started with **no tables**: those databases' datasource configurations set `hbm2ddl-auto: none`, and the `flyway` dependency brought a placeholder `V1__init.sql` that created none of the entities' tables. Only H2 (`ddl-auto: create-drop`) made a schema. Now a fullstack request whose resolved dependencies include **`flyway`** gets its schema as `backend/src/main/resources/db/migration/V1__init.sql`, and an update of such a project gets what the model changed as a migration of its own. A request without `flyway` keeps its bytes — no golden manifest moved. Liquibase is not served; the plain SQL wizard's baseline (*Round 10, phase 3*) is unrelated and unchanged.

- *The schema (`Schema`, `SchemaBuilder`).* A database-neutral model — tables, columns (`ColumnType`: `VARCHAR`, `TEXT`, `BIGINT`, `INTEGER`, `BOOLEAN`, `DATE`, `TIMESTAMP`, `TIME`, `INSTANT`, `DECIMAL`, `MONEY`, `UUID`, `BLOB`), keys, unique constraints, foreign keys, indexes — built from the entity definitions **the way `Entity.java.mustache` is rendered from them**: names through `EntityScaffoldContext.tableOf` / `schemaOf` / `columnOf` / `joinColumnOf` and the join-table helpers `joinTableOf` / `ownerJoinColumnOf` / `inverseJoinColumnOf` (now public; the last three were inline in the view-model and are shared with it), and the audit columns, `version` and `deleted` from the per-entity context's `auditApplicable` / `lockingApplicable` / `softDeleteApplicable` — the flags the template itself is gated on. `SchemaBuilder.typeOf(FieldType)` is an exhaustive switch. A view (`@Subselect`) has no table; a MANY_TO_MANY has its join table (both columns the key); a FILE or IMAGE field is a plain UUID column (the entity maps no association, so no foreign key); `app_attachment`, `app_saved_view` and `app_workflow_move` are added on the project flags (`hasAttachments`, `hasSavedViews`, `hasWorkflowMoves`) and written out by hand to match their entity templates. **A change to how an entity is mapped belongs in `SchemaBuilder` too** — the smoke build below is what fails when they drift. Beyond what Hibernate would create: an index on every foreign key (none of the four server databases makes one) and on a workflow's status and assignee columns. Enum columns get no CHECK constraint (a new enum value would need a migration to change it). Constraint names are `pk_<table>`, `uk_`/`fk_`/`ix_<table>_<column>`, lower case, cut to 60 characters with a hash. Exact-case names (`"x"`, `` `x` ``, `[x]`) are written in double quotes, which all five databases read.
- *Per database (`SchemaDialect`: `H2`, `POSTGRESQL`, `ORACLE`, `MSSQL`, `DB2`).* The migration is written for the first of PostgreSQL, Oracle, SQL Server, DB2 among the project's dependencies, else H2 (`SchemaDialect.of`). The type names are **the ones Hibernate's own dialect writes** for the templates' mappings, and `SchemaDialectTest` holds the table to that without a database: it has Hibernate export `dialectfixture.DialectFixture` (one column per shape the templates emit) for each dialect — H2 2.2, PostgreSQL 14, Oracle 19, SQL Server 2019, DB2 11.5 — and compares every column. Two deliberate differences, both in the test: H2's long text is `text` (H2's name for its CLOB, and what the entity's `columnDefinition = "TEXT"` says), and PostgreSQL's identity is `bigint generated by default as identity` where this Hibernate still writes `bigserial`. Long text is `text` / `clob` / `varchar(max)`. A unique constraint over a nullable column is a plain constraint on H2, PostgreSQL and Oracle, and a unique index that leaves nulls out on DB2 (`exclude null keys`) and SQL Server (`where c is not null`), as Hibernate's dialects do. `create schema if not exists` is written for H2 and PostgreSQL only; elsewhere a comment says the schema must exist. **The fixture lives outside `com.menora.initializr`**: the application scans that package for entities, and one more `@Entity` there fails the catalog database's `ddl-auto: validate` in every Spring test.
- *The baseline (`SchemaSql.baseline`, `SchemaMigrations.writeBaseline`).* Tables first, each with its key and inline unique constraints; then unique indexes, foreign keys and indexes — so tables that refer to each other, or to themselves, need no order. Written by `FullstackProjectGenerationConfiguration` after the render (the contributor is `@Order(50)`, after the catalog's file contributor, so it replaces the dependency's placeholder), from Java, not a template row. The same call turns `ddl-auto` / `hbm2ddl-auto: create-drop` (the H2 configurations) into **`validate`** in `application.yaml`: with a migration there, Hibernate creating the tables as well would hide a migration that does not match the entities until the first real database. The server databases' `hbm2ddl-auto: none` is left alone.
- *Updating (`SchemaDiff`, `SchemaMigrations.carryBaselineOver`).* `POST /starter-fullstack.patch` generates both sides; the contributor leaves the schema it wrote in `EntityDefinitionContext.generatedSchema()` and `generateSide` takes it out before the contexts are cleared. When both sides have Flyway and the same database: the target tree's `V1__init.sql` is replaced by the base's (**it has run; it never changes**), and the difference between the two schemas is added as `db/migration/V<yyyyMMddHHmmss>__model_update.sql` — a timestamp, because the project may have hand-numbered migrations the generator cannot see (a hand-written one added later needs a timestamp too, or `outOfOrder`). No schema change, no file. One side without Flyway, or two different databases: nothing special — the baseline that appears, goes or changes is the update.
  - **Live** (runs as written): a new table with its constraints and indexes; a new column that may be null or has a default (`deleted`); a foreign key, an index and a unique constraint on columns this migration adds; `NOT NULL` dropped; a constraint or an index the model no longer has.
  - **To review** (commented out, each under a wrapped `--` note saying what changed): a dropped column — with the foreign key, unique and index on it first, which SQL Server needs — or table; a changed type or length; a column that became required; a unique constraint or a foreign key over values that are already there; a changed key (a note only). **A required new column is added without `NOT NULL`** (live) and the `NOT NULL` is the review item: the table may have rows. **A rename is a removal and an addition** — the model cannot say otherwise — and the note on the removal says to rename instead.
  - The `ALTER` spellings are per database (`SchemaDialect.addColumn`, `setNotNull`, `dropNotNull`, `alterType`, `dropIndex`). `UPDATE.md` gains a "The database" section when the update carries such a migration (`ProjectUpdateBuilder.notes`).
- *Built for real* (`GeneratedBackendBuildSmokeTests`, `-Dsmoke.be=true`): `flywayBaselineIsTheSchemaTheEntitiesExpect` builds seven backends with `flyway` — Orders with every option and Approvals with the move log (both with their live API tests), the field-types, many-to-many and one-to-many models, Course enrolments (composite keys) and Project planning — and each starts on the schema the migration made with Hibernate validating; a test added to each project reads `flyway_schema_history`. `anUpdatesMigrationTakesTheOldSchemaToTheNewEntities` writes the old model's baseline and the update's migration, as generated, into the new model's backend and builds it.

*Limits.* **Only H2 has been run.** The PostgreSQL, Oracle, SQL Server and DB2 output is held to Hibernate's own type names and reviewed by hand; no statement of it has been executed on those databases — try the baseline on an empty one before relying on it. Open points there: `lower()`/`LIKE` search over a `clob` (Oracle, DB2); `varchar2(4000 char)` for the saved views' state on an Oracle without extended strings; DB2 needs `REORG TABLE` after some of the review statements (the notes say so). A table or column named like one of a database's keywords (`order`, `comment`, `level`…) is written unquoted, as the entity maps it, and fails on that database in the migration as it would in Hibernate's own queries — the model has to quote it or name it otherwise. The update's migration is the difference between two models, not a look at the database: a schema changed by hand, or made by Hibernate rather than by the baseline (other constraint names), is not what it assumes. Both sides are generated by today's generator, so a change in how the generator maps something shows up in the next update's migration. An existing project that adds `flyway` gets the whole schema as `V1`, which the dependency's `baseline-on-migrate` marks as applied on a database that already has tables.

Pinned by `SchemaDialectTest`, `SchemaDiffTest` and `FullstackMigrationTests`.

**OpenAPI wizard: interfaces, forms and security (2026-11).** The wizard's controllers were concrete classes with `TODO` bodies, so an update of the spec (`POST /starter.patch`) patched the very files a team had filled in; a `multipart/form-data` body became a JSON `@RequestBody` record (a 415 at runtime); and the document's security schemes were ignored. All in `openapi/OpenApiCodeGenerator`, with `FormField`, `SecurityUse` and `OperationModel.bodyKind/formFields/security`.

- *`apiStyle`* (`openApiOptions.<dep>.apiStyle`: `classes` | `interfaces`; `OpenApiWizardOptions.ApiStyle`). **Absent is classes — every request and saved model that names no style generates the bytes it did** (no golden manifest moved); the Backend tab's OpenAPI drawer starts a *new* setup on interfaces. With `interfaces`, each tag is `<api>/<Tag>Api.java` (`templates/wizard/openapi/Api.java.mustache`): every mapping, binding, constraint, `@ResponseStatus` and security annotation, each method a `default` that throws `ResponseStatusException(NOT_IMPLEMENTED)` — and `<api>/<Tag>Controller.java` (`ApiController.java.mustache`), `@RestController @Validated … implements <Tag>Api {}`, which **names nothing of the document but the tag**: a changed spec rewrites the interface and leaves the class alone, so an update never patches the team's code, and an operation the spec adds answers 501 until overridden. Spring MVC maps an interface's annotated (default) methods and an override's parameters through the interface. An override declares the signature only — Hibernate Validator refuses an override that adds parameter constraints (the class Javadoc says so). A removed tag's class is deleted by the update like any generated file.
- *Form bodies.* With no `application/json` content, a `multipart/form-data` or `application/x-www-form-urlencoded` body is read as its properties (`SchemaSet.propertiesOf`, references and `allOf` followed), each a parameter of its own — the openapi-generator way, and what binds a wire name that is not a Java name: a `format: binary` property is `@RequestPart MultipartFile` (an array of them `List<MultipartFile>`), an object in a multipart body a JSON `@RequestPart` of its record, anything else `@RequestParam` with its constraints and date format; the mapping gets `consumes`. No record is made of the body. A form-urlencoded object property travels as `String`. The client takes a `Resource` for a file and builds a `MultiValueMap` — files and JSON parts as they are, plain fields as their text (a date would otherwise go as a JSON part) — with the content type set (RestTemplate headers, RestClient `.contentType`). A property is required when the schema requires it and the body is not `required: false`.
- *Security* (`components.securitySchemes`; an operation's `security`, else the document's; `[]` or only `{}` alternatives = open). Server: the wizard adds springdoc with controllers, so the schemes are declared in `<api>/OpenApiSecuritySchemes.java` (`@SecuritySchemes`, every scheme of the document; OAuth2 without its flows) and each operation carries `@SecurityRequirement` per scheme it may be called with. Without springdoc (only through the generator's API) the method Javadoc says which schemes and that the gateway or the application enforces them. **Nothing is enforced by the generated code.** Client: each operation sends its **first** requirement's schemes from `<client>/OpenApiCredentials.java` — an API key in a header, a query parameter (RestClient `queryParamIfPresent`) or a cookie, `setBearerAuth` for HTTP bearer, OAuth2 and OpenID Connect (a token got elsewhere), `setBasicAuth` — each read from `<base-url property's parent>.security.<scheme-kebab>.api-key|token|username|password` (`${…:}`, empty by default and in the `application.yaml` stub; an environment variable or Vault gives the value) and **not sent while empty**. Digest and mutual TLS are documented, not sent.
- *Names.* `form`, `credentials` joined the reserved parameter names; `MultipartFile`, `Resource`, `MediaType`, `RequestPart`, `ResponseStatusException`, the springdoc security types and `OpenApiCredentials` the reserved type names (a schema called one gets `Dto`).
- *The editor.* The drawer's *Server code as* (Interfaces | Classes) shows with a server side; the entry keeps `apiStyle: 'interfaces'` only, the request sends it only with controllers, the model import reads the server's `INTERFACES`.

*Limits.* OAuth2 flows are not declared for Swagger UI, and the client does not fetch a token. Only the first security requirement is sent. A form property that is an object (urlencoded) or a free-form map (multipart) is text. Header/cookie API keys and bearer tokens set by a parameter of the same name would be sent twice. The update of a project whose spec drops a tag deletes that tag's class.

Each row: when, actor, source, request id, entity type, table, row id, CREATE/UPDATE/DELETE, a label (the row's depId, setKey, path, name…), the row before and after as JSON (references as ids, collections left out, normalized through JSON text), the changed fields; an UPDATE that changed nothing is not logged. - *Sources* (`CatalogChangeContext`): "admin" for a signed-in request, narrowed by the endpoint — "import" (`/admin/import`), "catalog-sync" (`/admin/catalog-sync/apply`), "template-reset" (`/admin/entity-template-sets/reset`), "restore"; at start "release-sync" by "system" for what the syncs do to an existing database (one request); the first seeding of an empty database is not logged (suppressed). **A scope must enclose the flush**: `DataSeeder` flushes inside its scope because its own transaction commits after it; a scope set inside a `@Transactional` method would log its changes as "system".
- *Restoring* (`CatalogHistoryService`, `CatalogHistoryController`, behind the admin login). `POST /admin/history/{id}/undo` puts the row back as it was before the change — a created row removed, a deleted one re-inserted **with its own id** (JDBC insert from the logged columns, then logged as CREATE, so whatever referred to it finds it again), an update reversed; `POST /admin/history/{id}/restore` takes the row to the version the change made; `POST /admin/history/requests/{requestId}/undo` undoes a request's changes last-first in one transaction (an import of hundreds of rows back to the ids it replaced). Undo first checks that the row is still as the change left it; otherwise 409 `{detail, rows}` naming the rows and the fields changed since, unless `{force: true}`. Everything a restore does is logged as "restore" by whoever asked; the metadata cache is rebuilt after. `GET /admin/history` (filters: entityType, rowId, actor, source, requestId, from, to, q; paged), `/admin/history/requests` (grouped), `/admin/history/{id}`.
- *Tried on a copy of the real database*: V28–V31 applied; the start's template sync was logged as one "release-sync" request of 92 changes; an admin's edit, its undo and a forced undo as expected.

*Limits.* One admin role. The log is kept for ever (no retention). Rows the release ships are re-seeded by their own rules (the template sync puts a deleted shipped template file back on the next start regardless of an undo). A restore of a row whose referenced row is gone fails on the foreign key — undo the parent first, or the whole request. The UPDATE of a row saved from outside Hibernate's view (a detached entity without loaded state) is logged without "before" and cannot be undone.

**SQL wizard from a live database (2026-11).** The SQL wizard and the fullstack DDL import took pasted DDL only. Both can now read the tables and views of a live PostgreSQL, SQL Server, Oracle or DB2 for IBM i database: through a **source** an admin set up, or a database typed in by hand.

- *Reading* (`liveschema/`). `LiveSchemaReader` uses JDBC `DatabaseMetaData` for tables, views, columns, the primary key, foreign keys (grouped by constraint, in key order) and unique indexes. It adds one catalog query per dialect for CHECK constraints (`pg_constraint`, `sys.check_constraints`, `ALL_CONSTRAINTS`, `QSYS2.SYSCST`/`SYSCHKCST`), Oracle's identity columns (`ALL_TAB_IDENTITY_COLS`) and PostgreSQL's enum types (`pg_enum`, read as a list of values). `CheckClauses` reads each database's spelling of `col IN ('A','B')` back as a list: PostgreSQL's `= ANY (ARRAY[…]::text[])`, SQL Server's OR chain of `[col]='A'`, and the text as written elsewhere. Anything else is not an enum. A connection is read-only, opened for one call and closed after it. Every statement has a 30 s timeout and the login 10 s. At most `menora.live-schema.max-concurrent-reads` (4) reads run at once; the rest wait 5 s, then get a 429.
- *What differs per database* (`DialectSupport`): the driver, the URL **built from parts** (host, port, database or service name, the DB2 library — never a URL from the caller, so no driver property such as a socket factory or an H2 `INIT` can be slipped in; `ConnectionSpec` checks each part), the timeout properties, the system schemas left out, the fold case, and how a driver's `TYPE_NAME`/`COLUMN_SIZE`/`DECIMAL_DIGITS` is written back as a type `TypeMappers` reads. Examples: `int8`→`BIGINT`, `bpchar`→`CHAR(n)`, `nvarchar` of 2^30-1→`NVARCHAR(MAX)`, SQL Server's `"bigint identity"`→`IDENTITY(1,1)`, Oracle's NUMBER without precision, `TIMESTAMP(6) WITH TIME ZONE`, DB2's `FOR BIT DATA`. An unknown type reads as text.
- *One path through text* (`LiveDdlWriter`). What was read is written as the script a person would have pasted: a `CREATE TABLE` per table (identity, NOT NULL, primary key, `UNIQUE (…)`, `CHECK (col IN (…))`), then the foreign keys **between the tables read** as `ALTER TABLE … ADD FOREIGN KEY` (so the script also runs as the Flyway baseline whatever the order; a key to a table not read is a comment, and the column stays a plain field), and a `SELECT <columns> FROM <view>` per view. A name is bare when it is a plain word in the fold case and not a keyword, otherwise quoted (`"OrderDate"`, `[User]`). The schema is kept (`hr.employees`, so `@Table(schema = …)`) unless `qualify: false`. The SQL wizard therefore generates exactly what that script pasted would, and the person sees and can edit it first.
- *Endpoints* (`config/LiveSchemaController`). Open, like the wizards; the access gate applies. `GET /metadata/live-schema/options` returns the enabled sources (name, dialect, description, default schema — not where they are), whether typed connections are allowed, which drivers are installed, the default ports and `max-tables`. `POST /metadata/live-schema/schemas` takes `{connection}` and returns `{schemas, defaultSchema}`: the source's default schema, else the one the connection opened in. `POST …/tables` takes `{connection, schema}` and returns `{tables: [{name, kind: TABLE|VIEW}], truncated}`, at most 5000. `POST …/ddl` takes `{connection, schema, tables, qualify?}` and returns `{dialect, sql, tables, views, warnings}` for the SQL wizard. `POST /metadata/fullstack/import-live` takes the same body and returns `{entities, note}`. Its tables go through `SqlToEntityDefinitionConverter.convert` over that DDL, so a key between two read tables becomes a relation and a CHECK list an enum. Each view comes through `convertSelect` with its fields **typed from their columns** (`SqlToEntityDefinitionConverter.fieldTypeOf`), and the note says the first column was made the key. `connection` is `{source}` or `{dialect, host, port?, database?, library?, user, password, trustServerCertificate?}`. Errors are `{error, detail}`: 400 for a bad part, an unknown table, a failed connect or a missing driver (the driver's words, with the password taken out); 403 when typed connections are off or the host is not allowed; 404 for an unknown source; 429 when busy. Each read is logged with the source or `host/database`, the schema, the count and the `userinfo` header — never the password.
- *Typed connections* (`menora.live-schema.typed-connections`, default true). Anyone may name a database, so the server connects wherever they say. `menora.live-schema.allowed-hosts` (comma-separated globs, `*.menora.co.il`) limits that, and is worth setting per environment. A typed password is sent with each call and kept nowhere, on the server or in the browser.
- *Admin sources* (`V32`, `initializer_schema_source`, `db/entity/SchemaSourceEntity`, `admin/SchemaSourceAdminController` at `/admin/schema-sources`). A source holds the parts plus the user. The **password is not stored**: `passwordRef` names the environment variable `SCHEMA_SOURCE_…` or the property `menora.live-schema.secrets.…` that holds it (`LiveSchemaService.PASSWORD_REF`; anything else is a 400, so a source cannot be pointed at `admin.password` or the datasource's). The list says `passwordAvailable`. `POST /admin/schema-sources/test` connects with a form, saved or not, and reports the schema count or why it failed. Sources are in the catalog history (`TRACKED`) and **not** in admin export/import (they name this environment's databases and secrets).
- *Drivers.* PostgreSQL, SQL Server and Oracle are runtime dependencies of the application (the versions the application's Boot manages). DB2 for IBM i (`net.sf.jt400:jt400:20.0.6`) is in the `db2-driver` Maven profile (`mvn package -Pdb2-driver`) because it is not in the offline repository. Without it DB2 is offered as "no driver on this server". Code uses `java.sql` only.
- *Tests.* `menora.live-schema.allow-h2` (tests only) adds H2, an in-memory database by name. `LiveSchemaIntegrationTests` covers the endpoints over HTTP against such a schema, including the script generated into a project through `/starter-wizard.zip`, the fullstack import, the errors and the admin sources. `LiveDdlWriterTest` takes each driver's documented column descriptions through the writer and back through the SQL wizard's parser and the DDL import. `CheckClausesTest` and `LiveSchemaServiceTest` cover the typed-connection switch, the host list and the URL parts. `LiveSchemaDockerTests` (`-Dsmoke.docker=true`) reads real PostgreSQL 16, SQL Server 2022 and Oracle Free 23 servers in Docker and, on PostgreSQL, runs the script into an empty schema as a baseline — all three passed on 2026-11-16.

*Limits.* DB2 for IBM i has not been read from a server: there is no container, and jt400 is not in the offline repository. In the SQL wizard a view's fields are `String` (the wizard's SELECT views were always so); the fullstack import types them. A PostgreSQL enum column becomes a CHECK-limited text column in the baseline script, not the enum type. Writing to the real column then needs `stringtype=unspecified`. Indexes, defaults, comments, sequences and triggers are not read. Tables are read one round trip at a time (fine for tens, slow for hundreds; `max-tables` 300).

**Events wizard: Avro payloads (2026-11).** The events wizard (*Round 10, phase 4*) refused a message whose `schemaFormat` is Avro. It now writes Avro channels, with **no schema registry**: a message is the record in Avro's single-object encoding (a two-byte marker, the 8-byte fingerprint of the writer's schema, the binary record), so producer and consumer hold the same schema. No existing manifest moved; a document without Avro is written as before.

- *Reading (`AsyncApiReader`).* A message (2.x `schemaFormat` beside the payload, 3.x `payload: {schemaFormat, schema}`) whose format starts with `application/vnd.apache.avro` (`+json`, `+yaml` too) is `EventMessage.avro`; its schema may be written in place, a `$ref`, or its JSON text as a string. One channel is all Avro or all JSON — mixed is the channel's `problem`. `EventChannel.avro()`; `DetectedChannel.format` (`avro`/`json`) tells the drawer.
- *Schemas (`events/AvroSchemas`).* No Avro library in the offline repository, so the schemas are walked as trees. Sources: the Avro messages' payloads, and every `components.schemas` entry that is an Avro named type (`type: record|enum|fixed` with a `name`, or `{schemaFormat: avro, schema}`) — those are taken out of the JSON payload set. Each top-level schema is a file `src/main/avro/<full name>.avsc`; one without a namespace takes the payload package (so its class has a package); a named type defined twice the same way is written once (the later copy becomes its name); defined two ways, a payload that is not a record, a name nobody defines, a name Avro does not allow, or files that refer to each other in a circle are 400s with the reason. **The plugin reads every file with one parser and in no order of its own**, so the files others refer to are listed, dependencies first, as the plugin's `<imports>` (`avroImports`).
- *Build (`eventsBuildCustomizer` → `addAvro`).* With any Avro schema in the document: `org.apache.avro:avro` at `${avro.version}` (`EventsCodeGenerator.AVRO_VERSION`, 1.11.4 — the first 1.11 without CVE-2024-47561), and `avro-maven-plugin`'s `schema` goal at `generate-sources` over `src/main/avro` (`stringType` String, decimals as `BigDecimal`, the imports).
- *Code* (`templates/wizard/events/Avro*.java.mustache`): `AvroKafkaConfig` — `avroKafkaTemplate` (`KafkaTemplate<String, byte[]>`) and `avroListenerContainerFactory`, built from **the project's own `ProducerFactory` / `ConsumerFactory` settings** (the catalog `KafkaConfig`'s servers and SASL) with the value as bytes; the catalog's String beans stay for JSON channels. `<Channel>Producer` sends `payload.toByteBuffer()`; `<Channel>Listener` reads `Type.getDecoder().decode(bytes)`. Several kinds of message on one channel: the listener's `decode` tries each type's decoder — the fingerprint tells them apart (`MissingSchemaException` means "not this one") — and hands over a `SpecificRecord`. The classes are imported by simple name unless two of a channel's share one.
- *Tests* (`generateTests`): the producer's record out through a mocked template and back through the decoder; the listener reads one and refuses bytes that are not Avro. A test value is the record's all-arguments constructor with a simple value per field (`AvroSchemas.sample`: logical types as `Instant`, `LocalDate`, `BigDecimal` at the schema's scale…; a union with null gets `null`); a field type with no simple value (fixed, uuid) leaves that record without a round-trip test.
- *Verified.* `EventsAvroTest`, `ProjectGenerationIntegrationTests.eventsWizardWithAvroPayloadsAddsTheSchemasAndThePlugin`, the golden case `events__avro__tests` (fixture `wizard-fixtures/orders-avro-asyncapi.yaml`). The plugin is not in the offline repository, so here the check was by hand: the generated `.avsc` files parsed with Avro 1.11.3's own parser in the plugin's order, classes written to the SpecificCompiler's shape, and the generated sources and tests compiled and run against the real Avro runtime (round trips with every logical type of the fixture, dispatch by fingerprint, the template built from the catalog's settings). `GeneratedBackendBuildSmokeTests.eventsWizardAvroBackendCompilesAndPassesItsTests` builds it with the real plugin where Avro resolves: `-Dsmoke.be=true -Dsmoke.avro=true` — **not yet run**.

*Limits (Avro).* No schema registry (Confluent's or Apicurio's): the topic carries the fingerprint, not a schema id, so a consumer that must read an older schema adds it to its decoder by hand (the `AvroKafkaConfig` javadoc says how). Payloads must be records. Avro's protocol files (`.avpr`, `.avdl`) and `.avsc` files outside the document are not read.

**Deeper field model, phase 1 (2026-11): help text and unique keys.** Item 19 of the backlog, in three phases (help text and unique keys; an expression language and cross-field rules; show-when and computed fields). Projects without either are byte for byte what they were; the Projects example carries both (its golden manifests moved, deliberately).

- *Help text.* `FieldDefinitionDto.help` (NON_NULL; at most `MAX_HELP` = 300 characters, a 400 at `…fields[i]` past it) → `FieldDefinition.help` → `putText(fv, "help", …)` + `hasHelp`. The generated form passes it to `Field`'s existing `hint` (shown under the input while there is no error, and the input's `aria-describedby`); both frontend sets share `EntityForm`.
- *Unique keys.* `EntityDefinitionDto.uniqueKeys: [{fields: [...]}]` (NON_NULL) → `EntityDefinition.UniqueKey` (`FullstackRequestValidator.parseUniqueKeys`, each a 400 at `entities[i].uniqueKeys[k]`): two to eight members, each a non-key field or a MANY_TO_ONE link (case-insensitive, made canonical), no long text (Oracle and SQL Server index no LOB), no member twice, no two keys over the same set, at most ten keys, none on a SELECT-backed view, and **at least one member rows can differ in** — not all enums, yes/no fields and patterned texts, which the demo data and the generated tests cannot vary by row number. A composed child (rows edited in the parent's form) may have none: a save inserts the new rows before it deletes the removed ones, so a row replaced by one with the same key would clash (`checkComposition`).
  - The constraint is `uk_<table>_<col>_<col>…` (`SchemaBuilder.uniqueKeyName`, the same 60-character rule as every other name), in the entity's `@Table(uniqueConstraints = …)` (both backend sets; `uniqueConstraintsJava`) and in the Flyway baseline (`SchemaBuilder.tableOf` — the schema model already took several columns, so update migrations add and drop keys with no new code).
  - A clash: `ApiExceptionHandler` (gated `hasUniqueKeys`, from `EntityScaffoldContext.putUniqueKeys`, both render paths) looks for each key's constraint name in the driver's message, longest name first, and answers 409 with `detail` "Another Task has the same Project and Title" and `errors` on each member as a client knows it (a link by its `<field>Id`). Any other unique clash keeps its generic message. The frontend's api-client keeps a 409's `errors` for the form when the project has a key (`fieldErrors` was a 400's only), so the clash shows on the fields.
  - Demo rows: a member with a default value is varied by row number like a unique column (`seedExpression(…, distinct)`), and the loader leaves out a row that would repeat a key (a set per key, `java.util.Arrays.<Object>asList(row.getX(), …)`). The generated API tests already vary every value by row number.
- *Fixed on the way:* `EntityDefinition.withOpt` (an import page switches `csvImport` on for its entity) dropped the entity's `access`, so an entity with its own levels and an import page got the defaults. It keeps every property now (`FullstackFieldModelTests.anEntityWithAnImportPageKeepsItsAccessLevels`).
- *Schema limits* `maxHelp`, `maxUniqueKeys`, `maxUniqueKeyFields` join `GET /metadata/fullstack/schema`.
- *Verified.* `FullstackFieldModelTests` (the generated code, the 400s, the access fix); `GeneratedBackendBuildSmokeTests.liveApiOfAUniqueKeyBehaves` builds Projects on its Flyway baseline with demo data and the generated API tests, and drives it: a second task of one project and title is a 409 naming both, the same title elsewhere is fine, an edit into a clash is refused (H2 only).

*Limits (phase 1).* The clash is recognized by the constraint's name in the driver's message: H2, PostgreSQL, Oracle and SQL Server put it there; DB2 for i's SQL0803 may not, and then the generic 409 is all there is. Help text is in the form only (not the details or a table header). A soft-deleted row still holds its key.

**Deeper field model, phase 2 (2026-11): the expression language and rules.** Projects without rules are byte for byte what they were; the Projects example has three (its golden manifests moved, deliberately).

- *The language (`fullstack/expr`).* One line over the row's **own** fields: `Expr` (lexer + recursive-descent parser → `Lit`/`Ref`/`Unary`/`Binary`/`Call`; `or` < `and` < `not` < one comparison (they do not chain) < `+ -` < `* /` < unary `-`; `&&`, `||`, `!`, `=` are spellings of `and`, `or`, `not`, `==`; texts in either quotes; at most 500 characters), `ExprCheck` (types: number, text, yes/no, date, date-time, instant, time, enum; a name must be a field, an enum compares only with `==`/`!=` and with one of its own values, spelled as the constant in the output; `+` adds numbers, joins texts, or adds days to a date; `-` takes days from a date; UUID/FILE/IMAGE fields only inside `isEmpty`; functions `isEmpty today now daysBetween length abs round date('yyyy-mm-dd')`; each error says where, "(at character n)"), `ExprCode` (Java over `row` against the generated `rules/Expr.java`, TypeScript over `value` against `shared/ui/rules.ts`), `ExprEval` (the generator's own interpreter). **Semantics, the same in all three:** numbers are decimals (Java `BigDecimal`, so `2.00 == 2`), an empty value makes an operation empty and a comparison unknown, `and`/`or` are three-valued, division by zero is empty — and **a rule that comes out unknown holds** (asking for a value is Required's or `isEmpty`'s job). Phase 3 (show-when, computed fields) reuses it.
- *Wire.* `EntityDefinitionDto.rules: [{when?, check, message, field?}]` (NON_NULL) → `EntityDefinition.Rule` (`FullstackRequestValidator.parseRules`, a 400 at `entities[i].rules[k]`): `check` and `when` must be yes/no conditions; a message of at most 200 characters; `field` (where the message shows) one of the entity's fields, else the first field `check` reads (a check that reads none must say). At most 20; none on a read-only entity or a SELECT view (never saved), none on a composed child yet (the parent's save does not run them — `checkComposition`).
- *Backend (gated `hasRules`, both sets).* `rules/Expr.java` (the runtime), `rules/<Entity>Rules.java` (`violations(row)` → field → message, first per field; `check(row)` throws `web/RuleViolationException`), and `ApiExceptionHandler.handleRules` → 400 with `errors`, the same shape as bean validation, so the form shows it on the field. The service checks before **every save**: create, update, a workflow move, each row of a bulk change, and an import (each violation an `ImportError` of its row). Claim/release/assign (only the assignee changes) and the demo loader (straight to the repository) do not.
- *Frontend.* `validate<Entity>` runs the same checks after the field checks (`import * as rule from '@shared/ui/rules'`), a field's own error first.
- *The rows the generator makes must pass them (`RuleRows`).* The API tests' rows, the form test's valid row: for each field the rules read (and the generator may choose — not a key, unique, patterned or attachment field), candidates by type (numbers 1, 0, 10, 100… inside min/max; texts the usual and a long one; every enum value; yes/no; dates today ± 0/1/7/30/365 days; times; empty when optional), searched with backtracking until every rule holds — in every state the generated test puts the row in (none, the initial one, where its first move lands). Dates are counted from today (Java `LocalDate.now().plusDays(k)`, TS a `day(k)` helper in the test file), so a rule over `today()` holds on the day the tests run. **When no combination passes, the entity's API tests are blocked** with the reason naming the rule ("no row the tests can make passes its rule 2 (…)"), the existing mechanism for rows the tests cannot make — the project still builds; the form test's "passes a complete record" is left out. The update test never changes a field a rule reads. Demo rows keep their varied values (they bypass the rules); a date a rule reads is shifted by the chosen days, so two dates keep the order a rule wants.
- *Example.* Projects: a project ends on or after it starts; a task is due on or after it starts; a finished task (`when status == 'DONE'`) has an estimate.
- *Schema limits* `maxRules`, `maxRuleMessage`, `maxExpression`.
- *Verified.* `ExprTest` (parsing, every refusal, Java and TS output, the semantics), `RuleRowsTest` (a rule that must hold after the test's workflow move; the rule that stops a search), `FullstackFieldModelTests` (generated code, the blocked tests, the 400s); `GeneratedBackendBuildSmokeTests.liveApiOfTheFieldModelBehaves` (Projects with demo data, Flyway and its API tests — 21 tests, through the rules — plus a 400 on `endsOn`, an empty date holding, an estimate asked of a finished task on a create and an edit); `GeneratedFrontendBuildSmokeTests.fullstackFrontendRulesPass` (Projects' frontend lints, builds and passes its 28 tests).

**Deeper field model, phase 3 (2026-11): show-when and computed fields.** The last phase of backlog item 19. Projects without them are byte for byte what they were; the Projects example has one of each (its golden manifests moved, deliberately).

- *Wire.* `FieldDefinitionDto.showWhen` and `.formula` (NON_NULL), expressions in the phase-2 language → `FieldDefinition.showWhen`, `.formula` (`computed()`), `.requiredWhenShown`. `FullstackRequestValidator.checkDerivations` (once all the entity's fields are known; each a 400 at `fields[i]`): a show-when is a yes/no condition that does not read its own field; a formula comes out as the field's kind (`formulaType`: numbers, texts, yes/no, dates, date-times, instants, times — not enums, UUIDs or attachments) and reads no other computed field; a computed field is never required, has no default and no show-when; neither on a primary key, on a read-only entity or view, on a workflow's status or assignee (pass 2), or on a composed child (`checkComposition`). **A required field with a show-when becomes optional, `requiredWhenShown`**: no NOT NULL, no `@NotNull`, no client blank check — `EntityDefinition.allRules()` adds a rule `when <showWhen>: not isEmpty(<field>)` (backend message "must not be empty", the form's `t('required')`).
- *Backend.* `<Entity>Rules.derive(row)` — a show-when field cleared while its condition is not true, then each computed field set from its formula (`computedJava`: a whole number rounded half up, money to the cent, a text cut to its length — `Expr.toInteger/toLong/money/fit`) — runs before the rules: `apply(row)` = derive + violations, `check(row)` = apply + throw. The service's saves call `check`, the import `apply`, and **the demo loader `derive`** (so demo rows have their computed values; their rules still are not checked). A computed field's view is marked read-only like a workflow's status: no PUT, bulk or inline edit, no import column; a client's value is overwritten. The column is real (stored), so it sorts, filters, exports and charts like any.
- *Frontend.* The form: a show-when field is wrapped in `{rule.applies(<condition>) && (…)}` (with the wizard step's `show(...)` when there are steps — `guardOpen`/`guardClose`, put in `buildEntityContext` once `formHasSteps` is known); a computed field is a read-only input showing `rule.show(<formula>)` live (`computedTs`; a date-time as `rule.localMoment`, an instant as `rule.isoInstant`). `validate<Entity>` first clears hidden fields and computes computed ones in `value` (what the server will save), skips the field checks of computed fields, then runs the checks and rules.
- *Generated tests.* The update and search tests never use a computed or show-when field (the server may clear or overwrite it); the form test has no cases of their own. `RuleRows` never chooses a computed field, expands what a rule reads through formulas and conditions, and derives each scenario as the server would (`Derive`).
- *Example.* Projects: a project's *Days* is `daysBetween(startsOn, endsOn) + 1`; a task's estimate is shown once the task has started (`status != 'TODO'`).
- *Verified.* `FullstackFieldModelTests` (the generated derive, form guard, read-only computed input, validate, the required-when-shown rule, every refusal); `liveApiOfTheFieldModelBehaves` (days computed on a create and an edit whatever the client sends, an estimate cleared on a task to do and kept on one started — 22 tests in the generated project); `fullstackFrontendRulesPass` (lint, build, 26 tests).

*Limits (phase 3).* A formula reads entered fields only (no computed field reads another). A computed value is computed on save, so one over `today()` holds the day it was saved. A hidden field's own checks (length, range) are not run while it is hidden — it is cleared anyway. Show-when and formulas read the row's own fields; a composed child has neither yet.

*Limits (phase 2).* A rule reads the row's own fields only (not a linked row's). Messages are as written (one language). The editor's checker is a mirror (`ui/src/components/fullstack/expr.ts`); the server has the last word. Rules do not run on claim/release/reassign, on a composed child's rows, or on demo rows.

### Tool upgrade (2026-11)

The application itself, not what it generates: the generated projects' default Boot (3.2.1) and every generated byte are unchanged — no golden manifest moved.

- *Spring Boot 3.2.1 → 3.5.16* (`pom.xml` parent). Initializr 0.23.0 is built against Boot 3.5.10, so the tool had been running the framework on an older Boot than it was made for. It brings Spring 6.2, Hibernate 6.6, Flyway 11 and H2 2.3; nothing in `src/main` needed a change to compile, and `application.yml` needed none.
- *The jar keeps the catalog's dotfiles.* maven-jar-plugin 3.4+ (Boot 3.5's) leaves "default excludes" out of the jar — `static-configs/**/.gitignore`, `.dockerignore`, `.editorconfig` — and the start-up catalog sync then fails: "The shipped catalog could not be read". `maven-jar-plugin` `addDefaultExcludes=false` in the pom. **The test suite cannot see this** (it reads `target/classes`); only starting the jar does.
- *An upgraded install.* Started the jar on a copy of a real catalog database: H2 2.3 opens the 2.2 file and Flyway 11 continues Flyway 9's history (it was at 27 and applied the five newer migrations).
- *Schema table vs Hibernate 6.6* (`SchemaDialectTest`, which compares the migration's types with what the application's Hibernate exports). PostgreSQL: 6.6 writes the standard `bigint generated by default as identity`, which is what the migration already wrote, so the test's `bigserial` exception is gone. Oracle: 6.6 writes `generated by default as identity`, so `SchemaDialect.identityClause()` does too (it was `generated as identity`, i.e. ALWAYS; both insert the same way for IDENTITY ids, and BY DEFAULT also lets a person insert an id of their own). H2: 6.6 writes a native `enum ('A','B')` for an `@Enumerated(STRING)` column; the migration keeps `varchar(255)` with its CHECK, which 6.6's `ddl-auto: validate` accepts (tried) and 6.4 wrote itself — so one script fits projects on both Boot lines. The test records that as a known spelling, like H2's TEXT/CLOB.
- *Artifacts.* Eleven artifacts 3.5.16 needs were not in the local repository (the starters for cache, mustache, actuator and logging, spring-hateoas, logback, log4j-to-slf4j, jul-to-slf4j, commons-codec, ehcache 3.10.9, maven-clean-plugin 3.4.1). They came from Maven Central in one online run; **the company Artifactory has to carry them** before the tool builds there.
- *Not done.* Mockito warns that it attaches itself as an agent ("Please add Mockito as an agent"), which a later JDK will refuse; the fix (`-javaagent` through surefire's `argLine`, after JaCoCo's) needs maven-dependency-plugin 3.8.1, which is not in the local repository either. `wsdl4j` stays at 1.6.3: it is the last release there is.
